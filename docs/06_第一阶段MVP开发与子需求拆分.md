# 第一阶段 MVP 开发与子需求拆分

> 本文是 Lang API 第一阶段的开发与验收总纲。目标是在复用 New API 成熟能力的前提下，完成一个具有独立品牌、独立前端、独立 Portal API 和受控模型网关的可商用最小闭环。
>
> 产品范围见[QinghuaAPI 与 New API 功能对比](./02_青花API与NewAPI功能对比.md)，技术基线见[技术架构与技术选型](./04_技术架构与技术选型.md)，构建和部署规范见[前后端一体化构建与部署](./05_前后端一体化构建与部署.md)。

## 1. 核心结论

当前已经具备开始第一阶段开发所需的产品边界和架构决策，不需要先完成所有运营细节。

第一阶段拆为 12 个子需求，按以下顺序实施：

```text
LANG-P1-01 工程基线与一体化构建
  -> LANG-P1-02 New API 基线与本地运行环境
  -> LANG-P1-03 Portal API 公共基础
  -> LANG-P1-04 独立前端骨架与公开页面框架
  -> LANG-P1-05 认证与会话闭环
  -> LANG-P1-06 API Key 管理闭环
  -> LANG-P1-07 公共模型网关与真实调用
  -> LANG-P1-08 模型广场与开发文档
  -> LANG-P1-09 请求日志与基础用量
  -> LANG-P1-10 钱包、充值与个人设置
  -> LANG-P1-11 法律内容与公开站点收口
  -> LANG-P1-12 生产化加固与端到端验收
```

其中 `LANG-P1-01`～`LANG-P1-07` 构成第一条核心链路：用户登录、创建 API Key，并通过公开域名完成一次真实模型调用。后续需求补齐用户查看、充值、内容和生产运行能力。

## 2. 第一阶段要交付什么

### 2.1 最小商业闭环

第一阶段完成后，用户应当能够：

1. 访问具有独立视觉和品牌表达的网站；
2. 注册、登录、刷新会话和退出；
3. 创建、查看、编辑、启停和删除 API Key；
4. 查看可用模型、价格和接入文档；
5. 使用公开 Base URL 完成真实的模型调用；
6. 查看自己的请求日志、基础用量和余额；
7. 使用已确定的充值方式获得额度，或在充值未开放时看到明确的关闭状态；
8. 修改 New API 当前支持的个人资料；
9. 阅读用户协议和隐私政策。

运维人员继续在私网使用 New API 原生管理后台维护渠道、模型、倍率、用户和系统配置。

### 2.2 第一阶段不追求

- 完整复刻 QinghuaAPI 的六项概览指标和图表；
- 自研用户、账务、支付、渠道和模型路由底座；
- 自研管理员后台；
- 法律文档版本和用户同意审计；
- 完整模型元数据、复杂筛选和独立模型目录；
- OAuth、MFA、Passkey 和完整设备安全中心；
- 多机高可用、Kubernetes 和微服务拆分；
- 像素级复制 QinghuaAPI 或复用 New API 默认前端。

上述内容分别属于第二、第三阶段或实际运营需求出现后的演进项。

## 3. 已冻结的设计决策

| 编号 | 决策 | 实现含义 |
|---|---|---|
| D01 | New API 是第一阶段业务数据权威 | 不建立第二套用户、Key、余额、日志和充值数据 |
| D02 | New API 管理后台只在私网使用 | 不修改、不复制其管理员前端，也不向普通用户开放 |
| D03 | 浏览器不直接访问 New API | 所有用户控制面请求通过 `/portal/api/*` |
| D04 | Portal API 使用白名单适配 | 不透明转发 New API 的全部 `/api/*` |
| D05 | 前后端逻辑分层、物理合包 | React 构建产物打入 Spring Boot JAR，发布一个 `lang-api` 镜像 |
| D06 | 同源提供页面和 Portal API | 前端只使用相对路径，不依赖 CORS |
| D07 | 模型数据面绕过 Portal API | Nginx 仅按公开协议路径白名单转发到 New API Relay |
| D08 | 第一阶段允许沿用 New API 数据口径 | 不为匹配参考站字段而阻塞已有能力上线 |
| D09 | 对外契约归 Lang API 所有 | 路径、DTO、错误码和响应头不暴露 New API 实现 |
| D10 | 一次部署不等于单容器 | Nginx、lang-api、New API、PostgreSQL、Redis 由 Compose 统一编排但独立运行 |
| D11 | 正式构建由根 Maven 统一编排 | 前端安装、测试、构建、资源复制和后端打包由一个入口完成 |
| D12 | QinghuaAPI 只作为功能参考 | 页面结构、样式、文案和组件必须形成独立产品表达 |

## 4. 第一阶段统一接口约定

### 4.1 Portal API 成功响应

```json
{
  "requestId": "req_xxx",
  "data": {}
}
```

### 4.2 Portal API 失败响应

```json
{
  "requestId": "req_xxx",
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "请求参数不正确"
  }
}
```

### 4.3 分页响应

```json
{
  "requestId": "req_xxx",
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "total": 0
  }
}
```

Portal API 不返回 New API 的原始响应包装、内部错误、私网地址、渠道 ID、节点名、堆栈或数据库错误。

### 4.4 时间和金额

- 接口时间使用带时区的 ISO 8601 字符串；
- 服务端存储和计算使用 UTC，页面按用户时区显示；
- 额度和金额的换算只在后端集中实现；
- 第一阶段必须明确显示币种或额度单位，不能只返回含义不明的数字；
- 前端不得自行复制 New API 的 quota 换算公式。

## 6. 子需求拆分

### LANG-P1-01：工程基线与一体化构建

**目标**

建立后续所有功能共享的工程结构，并证明前后端可以一次构建、一次打包。

**实现范围**

- 初始化根 Maven 工程和 `portal-api` Spring Boot 3.5.x 模块；
- 初始化 `frontend` React、TypeScript 和 Vite 工程；
- 锁定 Java、Maven、Node.js、npm 和前端依赖版本；
- 根 Maven 编排 `npm ci`、前端检查、Vite 构建和静态资源复制；
- 将前端产物复制到后端 `target/classes/static`；
- 配置 React Router 页面回退，同时排除 `/portal/api/*` 和 `/actuator/*`；
- 增加多阶段 `Dockerfile` 和 `.dockerignore`；
- 增加最小健康检查和应用版本信息；
- 建立后端、前端和集成测试目录。

**边界**

- 不实现业务页面和 New API 接口；
- 不把生成文件写入 `src/main/resources`；
- 不把 Node.js 放入最终运行镜像；
- 不在此需求引入数据库、消息队列或微服务模块。

**验收**

- 指定 Maven 命令可从干净工作区完成前后端构建；
- JAR 在没有 Node.js 的环境中可启动；
- `/` 返回 React 页面，刷新一个前端路由不会返回服务器 404；
- 不存在的 `/portal/api/test` 返回 JSON 404 而不是 `index.html`；
- 最终镜像以非 root 用户运行，且不包含源码、`node_modules` 和构建工具；
- 后端、前端最小测试均可由正式构建入口执行。

### LANG-P1-02：New API 基线与本地运行环境

**目标**

锁定真正用于开发和生产验证的 New API 版本，并建立可重复启动的完整本地依赖环境。

**实现范围**

- 选择并记录 New API Release、提交和容器镜像 digest；
- 逐项实测第一阶段所需的 New API 路由、方法、参数、响应和认证行为；
- 建立内部接口兼容性记录，标明已验证、差异和不可用项；
- 编写 Docker Compose，包含 `edge-nginx`、`lang-api`、`new-api`、`postgres` 和 `redis`；
- 建立内部网络、持久化卷、健康检查和启动依赖；
- 提供不含真实密钥的环境变量模板；
- 初始化 New API，并确认管理员后台只通过受控入口访问；
- 固定数据库初始化和升级路径。

**边界**

- 不修改 New API 源码；
- 不使用浮动 `latest` 作为生产基线；
- 不将数据库、Redis 或 New API 管理端口暴露公网；
- 不在仓库中保存真实供应商 Key、数据库密码或 Session 密钥。

**验收**

- 一条 Compose 命令能启动完整环境；
- 服务重启后 New API 数据仍存在；
- Portal API 可以通过内部网络访问 New API；
- 宿主机或公网不能直接访问数据库和 Redis；
- 已锁定基线的接口实测结果足以支持后续认证、Key、日志、余额、模型和法律适配。

### LANG-P1-03：Portal API 公共基础

**目标**

建立稳定的自有接口门面，使后续业务模块不直接依赖 New API 路径和 DTO。

**实现范围**

- 建立统一成功响应、错误响应、分页和 `requestId`；
- 建立参数校验、全局异常映射和 JSON 404；
- 建立 `upstream.newapi` 独立适配模块；
- 配置连接、读取、写入超时和连接池；
- 实现上游 Cookie、Header 和错误的集中转换；
- 建立敏感字段脱敏和结构化访问日志；
- 建立允许路径、方法、正文大小和响应字段白名单；
- 实现 `/portal/api/public-config`，只返回可公开配置；
- 使用 WireMock 或 MockWebServer 建立 New API 契约测试基础；
- 建立 Spring Security 基础规则和安全响应头。

**边界**

- 不提供任意 URL 代理能力；
- 不直接访问 New API 数据库；
- 不自动重试登录、创建 Key、支付等写操作；
- 不在日志中输出密码、Cookie、Access Token、完整 API Key 或支付签名。

**验收**

- 前端只能访问已声明的 `/portal/api/*`；
- New API 原始错误、响应头和私网地址不会透传；
- 超时、上游不可用、参数错误和未认证均返回稳定自有错误码；
- 日志可用 `requestId` 串联浏览器、Portal API 和上游请求；
- 上游 DTO 只存在于 New API 适配模块。

### LANG-P1-04：独立前端骨架与公开页面框架

**目标**

建立明显区别于 QinghuaAPI 和 New API 的前端产品骨架，为后续页面提供一致的视觉和交互规范。

**实现范围**

- 建立颜色、字体、间距、圆角、阴影和状态色等设计变量；
- 实现公开站点布局、登录后控制台布局和移动端导航；
- 建立路由、鉴权路由守卫、TanStack Query 和统一 API 客户端；
- 建立加载、空状态、错误、无权限和 404 组件；
- 建立表单、按钮、输入框、对话框、表格、分页和通知等基础组件；
- 建立中英文基础设施，第一批文案至少完整支持中文；
- 创建首页、模型广场、开发文档、登录、注册和控制台占位路由；
- 从 `/portal/api/public-config` 读取站点名称和公开 Base URL。

**边界**

- 不复制参考站的页面比例、导航细节、卡片排列和文案；
- 不复用 New API 默认页面源码或默认主题；
- 不在前端保存 New API 路径和响应 DTO；
- 不为尚未实现的功能伪造数据。

**验收**

- 桌面端和移动端基本布局可使用；
- 页面在视觉、导航结构和文案上能够明确识别为另一产品；
- 所有接口请求统一经过前端 API 客户端，并使用相对路径；
- 加载、空数据和错误状态不依赖浏览器默认表现；
- 构建产物中不包含 New API 私网域名和默认品牌。

### LANG-P1-05：认证与会话闭环

**进入前确认**

- 是否开放公开注册；
- New API 实际启用的验证码、邮箱验证和邀请机制；
- 正式 Cookie 域名策略。开发可以先使用本地域名配置。

**目标**

让用户通过自有页面和自有接口安全完成注册、登录、会话刷新、当前用户查询和退出。

**实现范围**

- 实现 `/portal/api/auth/register`；
- 实现 `/portal/api/auth/login`；
- 实现 `/portal/api/auth/refresh`；
- 实现 `/portal/api/auth/logout`；
- 实现 `GET /portal/api/profile`；
- 适配 New API 登录前置流程、验证码和认证状态；
- 重写 Cookie Domain、Path、Secure 和 SameSite；
- 实现前端注册、登录、登录态恢复、失效处理和退出；
- 为登录和注册增加基础频率限制与失败日志；
- 覆盖会话过期、重复退出、错误密码和禁用用户等异常。

**边界**

- 第一阶段不自建身份系统；
- 不把长期凭证保存在 `localStorage`；
- 不增加 OAuth、MFA 和 Passkey；
- 不把管理员角色能力带入普通用户前端。

**验收**

- 注册策略开启时，新用户可以注册并登录；关闭时页面和接口表现一致；
- 登录后刷新页面仍可恢复会话；
- 退出后旧会话不能继续调用受保护接口；
- Cookie 不包含 New API 私网域名，脚本无法读取 HttpOnly Cookie；
- 错误响应和页面中不出现 New API 品牌或原始提示；
- 未登录访问控制台会被引导到登录页。

### LANG-P1-06：API Key 管理闭环

**目标**

交付用户最核心的 API Key 全生命周期管理能力。

**实现范围**

- 实现 Key 列表、分页、名称搜索和状态筛选；
- 实现创建、详情、编辑、启停和删除；
- 适配额度、过期时间、模型限制和 IP 限制等 New API 已有字段；
- 第一版前端只展示已确认有价值的字段，高级字段可放入展开区域；
- 创建成功时提供一次明确的复制提示；
- 实现受控的 Key 显示或 reveal 接口；
- Key 列表默认只显示掩码；
- 对删除、启停和显示完整 Key 设置明确确认与错误反馈；
- 建立每个写操作的上游契约测试。

**边界**

- 不维护第二套 Key 数据；
- 不在日志、监控、埋点和错误报告中记录完整 Key；
- 不批量操作 Key；
- 不为了匹配参考站而隐藏 New API 已有且用户需要的关键限制能力。

**验收**

- 新建 Key 可在列表中看到且默认脱敏；
- 编辑、启停、过期、额度和模型限制在 New API 中真实生效；
- 删除后该 Key 无法继续调用；
- 用户不能读取或修改其他用户的 Key；
- 搜索、筛选、分页和空状态可用；
- 浏览器请求中看不到 New API 私网地址。

### LANG-P1-07：公共模型网关与真实调用

**进入前确认**

- 第一批开放的协议和路径；
- 至少一个可用模型供应商和测试额度；
- 正式 API 域名可以在上线前再替换，本地先使用测试域名。

**目标**

让 LANG-P1-06 创建的 Key 可以通过本项目公开 Base URL 完成一次真实模型调用。

**实现范围**

- 在 Nginx 建立 OpenAI 兼容接口的精确路径白名单；
- 根据已启用能力增加 Anthropic、Gemini 路径，未验证的协议不提前开放；
- 配置 Authorization 透传、请求大小、连接和读取超时；
- 正确处理 SSE 流式响应、禁用代理缓冲并支持客户端取消；
- 移除 New API 标识性响应头和默认错误页；
- 为非法路径、限流、上游超时和上游不可用提供稳定错误；
- 记录状态码、耗时和请求 ID，但不记录完整请求正文、响应正文和 Authorization；
- 增加普通响应、流式响应、取消、超时和路径白名单测试。

**边界**

- 模型请求不经过 Portal API；
- 不开放 New API `/api/*`、`/setup/*` 和管理页面；
- 已开始产生模型输出后不自动重试；

## 9. 第一阶段端到端验收场景

### 9.1 主链

1. 用户访问独立品牌首页并进入注册页；
2. 用户注册、登录并刷新页面，会话保持有效；
3. 用户创建一个限定额度和模型范围的 API Key；
4. 用户在模型广场选择一个真实可用模型；
5. 用户复制开发文档示例并通过公开 Base URL 发起流式请求；
6. 模型响应正常结束，费用只扣减一次；
7. 用户回到控制台，看到对应请求日志、用量和余额变化；
8. 用户禁用该 Key，再次调用得到预期的鉴权失败；
9. 用户查看充值记录、个人资料、用户协议和隐私政策；
10. 用户退出，受保护页面和接口不再可访问。

### 9.2 必须覆盖的失败链

- 错误密码和高频登录：返回自有错误并触发限制，不泄露账号是否存在；
- 会话过期：刷新成功或明确退出，不出现无限刷新循环；
- 越权读取 Key 或日志：服务端拒绝，不能仅靠前端隐藏；
- Key 额度不足、已过期、已禁用或模型不允许：网关返回稳定错误且不绕过 New API 校验；
- 模型流式响应中断：连接释放，不自动产生第二次模型调用；
- New API 不可用：Portal API 和模型网关使用自有错误，不暴露私网信息；
- 支付回调伪造或重复：拒绝或幂等，不重复增加额度；
- 未知前端路由和未知 API 路由：分别返回前端 404 页面和 JSON 404。
