# AGENTS 编写更新指引

请阅读当前代码仓库，为本项目维护一个适合 Claude Code 之外的 Codex 使用的 `AGENTS.md` 文件。

这个文件是“给 AI 编程代理看的项目作业指导书”，不是 README 的重复版。它应该帮助 AI 在每次开发前快速理解：项目做什么、代码放哪里、怎么运行和测试、有哪些架构边界、哪些事情不能做、做完后如何验证。

## 使用原则

- 这份指引是 `AGENTS.md` 后续更新时的参考依据，不应被全量、机械地搬进 `AGENTS.md`。
- 更新时应结合当前仓库实际情况按需选取章节，只保留真正有用、具体、可执行、可验证的内容。
- 找不到的信息写 `TODO`，并说明需要补什么。
- 不要复制 README 的大段内容。
- 不要写空泛口号，例如“代码要优雅”“要高质量”。
- 不要把完整数据库表结构、完整接口文档、全部历史需求塞进去。
- 对“仓库结构”这类内容，不必拘泥于固定示例形式；可以使用列表、树状结构或其他更适合当前仓库的表达方式。

## 章节长度与自动抽取

- 主文件 `AGENTS.md` 应保持精简。
- 当任一章节（含子节）正文超过 **80 行** 时，应将该章节抽取为独立文件 `docs/agent-guidelines/sections/{章节名}.md`，并在主文件中保留章节标题与一行链接引用。
- 抽取后主文件该章节只保留：标题 + 一两句概述 + 指向独立文件的链接。
- 后续如果某个独立章节继续膨胀，可以在该章节文件内部再拆子文件，但主文件仍只引用入口文件。

## 建议优先保留的信息

- AI 每次开发前都需要知道的信息
- 会直接影响代码放置、运行、测试、验证的信息
- 会影响依赖方向、架构边界和禁止事项的信息
- 项目中特有、容易误判或容易踩坑的信息

## 标准章节清单

`AGENTS.md` 初始化时会包含以下章节标题（业务章节内容为空，等待按需补充）：

1. 文档目的
2. 使用范围
3. 文档语言约束
4. 项目概览
5. 仓库结构
6. 开发命令
7. 测试与验证
8. 编码规范（默认已写入 Andrej Karpathy 规范约束的引用 + 项目特定编码习惯子节）
9. 架构规则
10. 工作流规则
11. 安全与禁止事项
12. 完成标准
13. 常见坑
14. 本文件的更新方式

后续按需补充每一节内容；不要为没有真实信息的章节强行编内容。

## 代码风格规范章节说明

- `编码规范` 是本 skill 默认要求保留的项目级章节。
- 主文件中只需要保留简短说明 + 四条原则要点 + 附件引用。
- 详细规范见：`docs/agent-guidelines/Andrej Karpathy 代码规范约束.md`
- 配套示例见：`docs/agent-guidelines/Andrej Karpathy 代码规范示例.md`
- 项目特定的编码习惯写在 `编码规范 → 项目特定编码习惯` 子节里；与 Karpathy 规范冲突时以子节为准。

## 各章节编写要点

### 1. 项目概览

作用：
让 AI 快速理解项目定位、核心目标、主要用户和关键业务概念，避免只看局部代码就误判项目方向。

应该写：
项目是做什么的；服务哪些用户、系统或业务场景；核心目标是什么；有哪些关键领域概念；项目明确不做什么。

不应该写：
宣传口号、公司愿景、过长背景故事、README 大段复制、与开发无关的信息、不确定或过时的信息。

### 2. 仓库结构

作用：
让 AI 知道每个目录负责什么，新代码应该放哪里，哪些目录不能随便改，避免随意创建目录或破坏已有结构。

应该写：
核心目录职责、代码放置规则、生成代码目录、废弃或历史目录说明、重要文件的位置。

不应该写：
完整文件树、每个文件逐一解释、与当前项目无关的目录、过时目录说明、和实际仓库不一致的结构。

说明：
仓库结构不必逐条罗列，也可以用树状结构表达，只要更贴合当前仓库并且便于 AI 快速理解。

### 3. 开发命令

作用：
让 AI 使用正确命令安装、启动、构建、检查和测试项目，避免猜错包管理器或运行不存在的命令。

应该写：
依赖安装命令、本地启动命令、构建命令、lint 命令、类型检查命令、全部测试命令、单个测试文件运行方式、必要本地服务、环境变量说明。

不应该写：
没验证过的命令、不存在的命令、与项目无关的通用命令、低频生产部署命令、危险的生产操作命令。

### 4. 测试与验证

作用：
告诉 AI 修改后如何验证，什么时候必须补测试，测试失败时怎么办，什么情况下不能声称任务完成。

应该写：
不同类型修改对应的测试方式；什么时候需要新增或更新测试；测试失败时应该优先修实现而不是削弱测试；无法运行测试时最终回复要说明原因和应运行的命令。

不应该写：
模糊的“尽量测试”、鼓励删除或削弱测试、只有全量测试没有局部验证方式、无法执行的测试要求。

### 5. 编码规范

作用：
让 AI 遵守项目已有代码风格，减少类型滥用、风格不一致、随意引依赖、错误处理混乱等问题。

应该写：
语言和框架规范、命名规则、类型规则、错误处理规则、日志规则、依赖引入规则、工具函数复用规则。

不应该写：
空泛的“代码要优雅”、与技术栈无关的规范、和现有代码冲突的规则、格式化工具已经能自动处理的细节、过细的个人偏好。

补充：
本 skill 已经在 `编码规范 → Andrej Karpathy 代码规范约束` 子节预填了通用约束；项目特定的编码习惯写在 `项目特定编码习惯` 子节里。

### 6. 架构规则

作用：
保护项目分层和模块边界，避免 AI 为了快速实现而跨层调用、混入业务逻辑或破坏依赖方向。

应该写：
分层职责、允许的依赖方向、禁止的依赖方向、模块之间如何通信、公共 API 约束、领域逻辑和数据库访问的边界。

不应该写：
过长架构论文、未落地到代码结构的抽象原则、与当前仓库不一致的架构描述、空泛的“保持架构清晰”。

### 7. 工作流规则

作用：
规定 AI 执行任务的工作方式，尤其是复杂修改时要先理解、再计划、再改动、再验证。

应该写：
小任务流程、复杂任务流程、重构规则、什么时候需要更新文档、最终回复应该包含什么。

不应该写：
过度复杂的流程、每个小改动都要求长方案、没有验证闭环的流程、AI 无法执行的异步流程。

### 8. 安全与禁止事项

作用：
明确 AI 不能做什么，尤其是安全、生产配置、数据库、敏感数据、金融逻辑和破坏性操作。

应该写：
不能提交密钥；不能修改生产配置；不能执行破坏性数据库操作；不能削弱测试；不能手动改生成文件；不能泄露敏感数据；不能随意修改关键业务逻辑。

不应该写：
笼统的“注意安全”、与项目无关的限制、把所有事情都禁止导致 AI 无法工作、无法验证的规则。

### 9. 完成标准

作用：
明确什么叫任务完成，避免只改代码但不测试、不说明风险、不更新文档。

应该写：
实现标准、测试标准、文档标准、检查标准、最终回复必须包含什么、不能完成时如何说明。

不应该写：
无法验证的完成标准、只写“代码完成”、忽略测试和风险说明、要求 AI 做无法实际完成的事情。

### 10. 常见坑

作用：
记录 AI 或新开发者容易踩坑的地方，减少重复错误。这个部分应该持续维护。

应该写：
项目特殊约定、容易误解的领域概念、常见环境问题、常见测试问题、生成代码注意事项、历史遗留限制。

不应该写：
一次性问题、已经修复且不会再出现的问题、太细碎的个人经验、没有实际影响的信息。

## 更新主文件时的判断标准

只有满足以下原则时，某一章节的内容才值得写进主文件：

- 与当前仓库真实情况一致
- AI 日常开发时高频需要
- 能直接指导代码修改、运行、测试或验证
- 具体、可执行、可验证

如果某一章节暂时没有足够信息，优先不写正文（只保留章节标题），或写一行 `TODO` 注明需要补充什么。
