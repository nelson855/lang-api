# 技术架构与技术选型

## 1. 选型结论

Lang API 采用以下技术架构：

> React 静态前端打入 Java/Spring Boot 模块化单体 Portal API，形成一个 `lang-api` 应用镜像；Nginx 负责公网入口和模型网关，New API、PostgreSQL 与 Redis 保持私网独立容器，由 Docker Compose 一次部署。

系统按流量性质划分为两个部分：

- **控制面**：处理账号、API Key、余额、模型目录、请求日志和法律文档等用户管理请求，由 Portal API 负责。
- **数据面**：处理模型推理、文件和流式响应等高流量请求，由 Nginx 按白名单直接转发给 New API Relay。

这样可以让自研工作集中在用户能够感知的产品层，同时避免在第一阶段重复实现模型路由、协议转换、计费和渠道管理。

## 2. 架构关系

![Lang API 总体架构](./assets/01_LangAPI总体架构.drawio.png)

可编辑源文件：[01_LangAPI总体架构.drawio](./assets/01_LangAPI总体架构.drawio)

```text
浏览器
  ├── 用户前端
  └── /portal/api/* → Portal API → New API

SDK / API 客户端
  └── 公共模型 API → Nginx 白名单网关 → New API Relay

私网
  ├── New API
  ├── New API 管理后台
  ├── PostgreSQL
  └── Redis
```

New API 管理后台继续原样保留，但只能通过 VPN、跳板机或 SSH 隧道访问。

## 4. 版本策略

### 4.1 Java 和 Spring Boot

- 使用项目当前配置的 Java 21；
- Spring Boot 使用成熟的 `3.5.x` 稳定版本线；
- 初始化工程时锁定当时最新的补丁版本；
- 不使用 `SNAPSHOT`、里程碑版本或浮动版本；
- 升级 Spring Boot 前执行完整测试和 New API 契约测试。

选择 Spring Boot 3.5.x 而不是直接追随最新大版本，主要是为了减少第三方库迁移和生产兼容风险。

### 4.2 New API

- 使用明确的 Release 版本或容器镜像 digest；
- 禁止生产环境使用会自动漂移的 `latest`；
- 测试环境验证通过后才能升级生产；
- 记录每次升级对应的数据库迁移和 Portal 适配变化；
- 只支持一个明确的生产基线版本，不同时兼容大量历史版本。

### 4.3 前端依赖

- 使用锁文件固定完整依赖树；
- 不使用宽泛的 `*` 或无上限版本范围；
- UI 组件升级必须检查视觉和交互变化；
- 构建产物必须可追溯到 Git 提交和依赖锁文件。

## 5. 前端架构

### 5.1 第一阶段采用静态单页应用

第一阶段以登录后的用户控制台为主，采用 React + Vite 静态构建。构建产物在 Maven 构建期间复制到 Spring Boot classpath，随 Portal API 一起打入 JAR 和容器镜像。生产环境不运行单独的 Node.js 前端服务。

主要原因：

- 部署简单；
- 前后端版本原子发布和回滚；
- 浏览器始终通过同源的 `/portal/api/*` 访问后端，无需开放 CORS；
- 前端服务故障面较小；
- 控制台不依赖搜索引擎收录；
- 与 Java Portal API 边界清晰；
- 后续仍可为公开页面增加预渲染。

如果 SEO 后续成为明确的获客瓶颈，再为首页、模型页和开发文档增加静态预渲染，不在第一阶段引入完整 SSR 服务。

### 5.2 页面模块

```text
frontend/src
├── app             应用入口、路由和全局 Provider
├── pages           页面级组件
├── features
│   ├── auth        登录和注册
│   ├── dashboard   数据概览
│   ├── api-keys    API Key
│   ├── usage       请求明细
│   ├── wallet      钱包和充值
│   ├── catalog     模型广场
│   ├── profile     个人设置
│   └── legal       法律页面
├── components      通用组件
├── api             Portal API 客户端和类型
├── design          设计变量和主题
├── i18n            国际化资源
└── docs            Markdown/MDX 内容
```

### 5.3 视觉独立性

- 不复制 QinghuaAPI 的布局尺寸、卡片比例和导航细节；
- 不使用 New API 默认组件和页面源码；
- 可以使用无样式基础组件，但必须自定义颜色、字体、间距、圆角和状态；
- 避免直接使用任何 UI 模板的默认主题；
- 页面只展示本项目需要的功能，不暴露底层配置概念。

## 6. Portal API 架构

### 6.1 采用模块化单体

Portal API 只有一个可部署应用，但内部按业务领域隔离：

```text
portal-api
├── auth            登录、注册、刷新和退出
├── profile         当前用户与资料修改
├── apikey          API Key 管理
├── usage           请求日志和用量
├── dashboard       统计聚合
├── wallet          余额、充值和交易视图
├── catalog         模型目录
├── legal           法律内容
├── upstream
│   └── newapi      New API 客户端、DTO 和字段转换
└── infrastructure  安全、错误、缓存、日志和监控
```

模块之间通过明确的 Java 接口协作，不直接使用其他模块的数据库实现或上游 DTO。

### 6.2 第一阶段保持无状态

第一阶段不创建独立 Portal 业务数据库。用户、Key、额度、日志和充值数据均以 New API 为准。

Portal API 只负责：

- New API 认证适配；
- 路径和字段转换；
- 响应字段裁剪；
- 统一错误格式；
- 接口白名单和权限检查；
- 短期缓存；
- 追踪与审计日志。

禁止 Portal API 和 New API 双写用户、余额或 API Key。

### 6.3 New API 适配层

所有 New API 调用必须集中在 `upstream.newapi` 模块。前端接口层不得直接拼接 New API 路径或依赖其响应 DTO。

建议按领域划分客户端：

```text
NewApiAuthClient
NewApiUserClient
NewApiTokenClient
NewApiUsageClient
NewApiWalletClient
NewApiPricingClient
NewApiLegalClient
```

每个客户端包含：

- 上游请求和响应 DTO；
- 超时设置；
- 错误转换；
- 敏感信息脱敏；
- 契约测试。

不对登录、注册、修改资料、创建 Key 和支付等写操作进行自动重试。

## 7. 公共模型网关

### 7.1 使用 Nginx 而不是 Java 转发模型流量

公共模型请求可能包含 SSE 流式输出、大文件、长连接和客户端取消。第一阶段通过 Nginx 转发可以避免 Portal API 重复承担流式协议实现。

Nginx 仅开放确认支持的路径，例如：

```text
/v1/chat/completions
/v1/responses
/v1/embeddings
/v1/images/*
/v1/audio/*
/v1/models
/v1/messages
/v1beta/models/*
```

实际白名单以所启用模型协议为准，不允许用一个宽泛规则开放 New API 的全部路由。

### 7.2 网关约束

- 流式接口关闭代理响应缓冲；
- 不缓存模型响应；
- 设置合理的连接、发送和读取超时；
- 限制请求正文大小和并发连接；
- 移除底层服务响应头；
- 返回自有 404、429 和网关错误；
- 已经开始转发请求后不自动重试；
- 不开放 `/api/*`、`/setup/*` 和默认管理页面；
- 不记录 Authorization、完整请求正文和完整响应正文。

当业务明确要求独立计费、请求内容审计或复杂实时风控时，再评估自研 Java/Go 数据面网关。

## 8. 数据和缓存

### 8.1 第一阶段

```text
New API → PostgreSQL
New API → Redis
Portal API → New API HTTP API
```

Portal API 不直接访问 New API 数据库。模型价格和法律正文可以使用 Caffeine 做短期缓存。

### 8.2 后续阶段

需要法律版本、模型展示元数据或统计聚合时，增加独立 Portal 数据库：

```text
PostgreSQL 服务
├── newapi 数据库 + 独立账号
└── portal 数据库 + 独立账号
```

即使共用 PostgreSQL 实例，也禁止共用业务表和数据库账号。

需要多节点共享缓存后，再为 Portal API 使用独立 Redis Key 前缀或独立 Redis 实例。

## 9. 认证设计

第一阶段继续使用 New API 的认证能力，不自建身份系统。

推荐流程：

1. 浏览器请求 Portal API 登录接口；
2. Portal API 完成 New API 登录前置流程并提交登录；
3. Portal API 转换响应，不返回底层实现信息；
4. 短期 Access Token 仅保存在浏览器内存；
5. Refresh Token 使用 `HttpOnly`、`Secure` 和合适的 `SameSite` Cookie；
6. Portal API 正确重写 Cookie Domain 和 Path；
7. 刷新、退出和敏感操作检查 Origin/CSRF 条件。

不得将长期登录凭证保存到 `localStorage`，不得在日志中记录密码、验证码、Cookie、Access Token 或完整 API Key。

## 10. 部署架构

### 10.1 第一阶段使用 Docker Compose

```text
compose
├── edge-nginx
├── portal-api
├── new-api
├── postgres
└── redis
```

只有 `edge-nginx` 暴露公网端口。`lang-api` 容器同时提供前端静态资源和 Portal API；New API、PostgreSQL 与 Redis 位于内部网络。

如果预算允许，生产环境优先使用托管 PostgreSQL，并确保备份、监控和恢复能力。Redis 可以先自托管，但不得暴露公网。

### 10.2 环境划分

至少保留：

- 本地开发环境；
- 测试/预发布环境；
- 生产环境。

测试和生产不得共用数据库、Redis、支付密钥、模型供应商 Key 和 Cookie 密钥。

## 11. 测试策略

### 11.1 Portal API

- 领域服务单元测试；
- New API 响应映射测试；
- WireMock/MockWebServer 上游契约测试；
- 认证 Cookie 和 Header 测试；
- 参数边界和错误转换测试；
- 敏感信息日志测试。

### 11.2 前端

- 表单和数据转换单元测试；
- 关键组件交互测试；
- Playwright 覆盖注册、登录、Key、日志、余额和退出流程；
- 响应式布局和中英文切换测试。

### 11.3 模型网关

- 普通响应和 SSE 流式响应；
- 客户端取消；
- 超时和大请求体限制；
- 路径白名单；
- 未授权、限流和上游失败；
- 确认禁止访问 New API 管理接口。

## 12. 可观测性

第一阶段采用轻量方案：

- Nginx、Portal API 和 New API 使用结构化日志；
- Portal API 为每个请求生成或透传 `requestId`；
- 日志中包含状态码、耗时和上游结果，但不记录敏感凭证；
- Spring Actuator 提供健康检查；
- Micrometer 输出基础请求指标；
- 对登录失败突增、模型错误率、支付回调失败和余额异常建立告警；
- 配置外部存活监控。

第一阶段不建设 Elasticsearch 日志集群。日志量达到实际瓶颈后再选择集中存储方案。

## 13. 工程目录

```text
lang-api
├── pom.xml             根构建入口，编排前端与后端构建
├── frontend/           React + TypeScript + Vite
├── portal-api/         Java 21 + Spring Boot
├── gateway/            Nginx 配置、白名单和错误页
├── deploy/             Docker Compose 和环境模板
├── integration-tests/  契约与端到端测试
├── Dockerfile          lang-api 多阶段镜像构建
└── docs/               产品和技术总纲
```

根 Maven 构建统一执行前端依赖安装、Vite 构建、静态产物复制和 Spring Boot 打包，最终只生成一个可部署的 `lang-api` JAR/镜像。Portal API 保持单一 Maven 模块起步，只有出现明确的编译隔离需求时才拆为多个 Java 子模块。具体构建与部署约束见[前后端一体化构建与部署](./05_前后端一体化构建与部署.md)。

## 14. 当前不引入的技术

第一阶段不使用：

- Kubernetes；
- Spring Cloud Gateway；
- Spring Cloud 全家桶；
- 微服务注册中心；
- 服务网格；
- Kafka 或 RabbitMQ；
- Elasticsearch；
- GraphQL；
- 自建 OAuth 服务器；
- 独立用户中心；
- 独立支付服务；
- 独立账务系统；
- 独立管理员后台。

只有当实际业务指标证明现有架构不足时，才增加相应组件。

## 15. 架构演进原则

1. New API 已有的能力先适配，不重写。
2. New API 有底层数据的功能，第二阶段在 Portal API 聚合。
3. 必须新增数据模型的功能最后开发。
4. 所有对外契约归 Lang API 所有，不让前端依赖 New API DTO。
5. 模型数据面和用户控制面保持分离。
6. 不共享 New API 数据库表，避免形成无法升级的强耦合。
7. 先通过垂直扩容和缓存解决问题，再考虑拆服务。
8. 每次增加基础设施都必须对应一个已经发生的实际问题。
