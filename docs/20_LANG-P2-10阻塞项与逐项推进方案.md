## 3. B1：实际调用链的观测接入

**初轮缺口（本次已解除）**：直接调用指标方法的测试通过，但生产调用链没有 `recordProtection` 调用，不能证明范围/页数/记录超限会产生拒绝计数。上游计数只在完整读取成功后记录，不能表示读取失败前已经发生的 HTTP 尝试。

**需要什么**：先明确“逻辑读取”（一次业务来源读取）与“HTTP尝试”（实际向上游发起的一次请求）的区别，以及成功、失败、拒绝时各指标如何计数。无需等待真实账号即可补充确定性测试和接入。

**推进步骤**：

1. 先写实际调用链的失败测试，覆盖30天早拒绝、页数/记录边界、单次/总超时和缓存命中。
2. 最小接入对应指标；拒绝原因与标签保持有限集合，不包含用户、模型、请求标识或密钥。
3. 明确已接纳页/记录与实际尝试页的区别；按确定的定义记录成功和失败路径，避免合并加载或多层处理重复计数。
4. 将 `observability` 从固定阻塞说明改为可执行检查，保存受控注册表证据及计数含义。不能把进程内测试指标说成真实容器指标。

**完成标准**：实际30天拒绝有对应计数，日志分页仍为零；其他保护与缓存场景计数符合定义；错误路径可解释；检查能随行为变化产生PASS/FAIL。发现明确不符合契约时应报FAIL，缺少观测前提才报BLOCKED。不新增公开监控端点。

### B1 本次结果与计数标准（2026-10-03）

- **结果**：3.5已完成。Dashboard与账户快照两个实际生产入口，经受控HTTP服务和进程内注册表验证16个场景；观测入口实际执行断言并通过敏感扫描保存[指标证据](../integration-tests/aggregation/report/b1/observability.json)。后端783项、0失败、0错误、1项既有跳过；验收工具17项通过。
- **逻辑读取**：`upstream.calls`按一次来源读取收口计1次，成功/失败分别标记；范围早拒绝也计1次失败逻辑读取，HTTP仍为0。缓存命中不读取来源，同查询并发共享加载只计1次读取。
- **HTTP尝试**：`upstream.http-attempts`在`NewApiExchange`执行HTTP请求的边界计数，失败和超时不撤销。覆盖成功/错误`log-self`来源，包括普通请求日志页面；它不是某一聚合请求独有的页数。生产传输禁用自动重试，不把未发起的后续页计入尝试。
- **已接纳页/记录**：`upstream.pages/records`只记录通过分页与预算检查的页/记录，失败读取也保留此前已接纳部分；拒绝页不接纳。第二页HTTP失败的例子是：失败逻辑读取1、HTTP尝试2、已接纳页1。
- **保护拒绝**：范围、页数、记录数、总截止时间、单次HTTP超时、分页不一致分别使用固定标签，由一次加载收口处记录1次，不随并发等待者重复记录。30天拒绝为`range=1`、HTTP=0、页/记录=0。
- **缓存与耗时**：缓存计数保持`hit/miss/coalesced`（命中/加载/共享加载）；失败加载没有成功缓存结果。沿用既有耗时口径：Dashboard成功耗时记录非命中查询，账户快照成功耗时包含命中查询；两者失败均记录，不能据此直接比较全部请求耗时。
- **剩余限制**：证据来自本地测试进程，HTTP源为受控来源，不是运行容器或真实New API指标。本次未重建或部署服务，B6/B7仍需当前构建和真实采样，不新增公开监控端点。

## 4. B2：真实双用户隔离

**初轮缺口**：只有真实匿名401证据，没有用户A与B之间的数据和缓存隔离验证。现已补齐可执行适配及非空真实样本；剩余失败为退出后的旧会话仍可使用。

**需要什么**：两名专用测试用户，各自可区分的Key、日志或流水，以及可读取的测试凭据。账号可复用已明确用于测试的既有身份，也可在受控本地环境创建；不要求用户一定手工提供。两个同样空的账号不足以证明数据隔离。

**推进步骤**：

1. 确认账号采用复用还是创建、数据归属，以及结束后保留还是清理测试账号/Key。
2. 补齐凭据读取、独立会话登录、资源记录和失败恢复适配，不输出身份及会话内容。
3. A/B查询同一范围，核对各自独有记录不会混入另一用户结果；再次查询验证缓存隔离。
4. 验证伪造用户参数、退出和会话失效；将结果接入验收入口。

**完成标准**：真实双用户隔离检查可重复执行，正常/失败均能完成约定的清理恢复；不得用客户端自报userId或仅比较两个空列表证明隔离。

## 6. B4：固定范围真实对账

对账是从原始来源独立计算预期值，再与Portal输出比较，不能用被测服务自己的计算逻辑生成预期。

**缺口**：当前 `reconciliation` 没有完整执行适配，本轮未在当前构建上固定身份、范围、筛选和定价复验。

**需要什么**：可重复读取的真实成功日志、基础定价及必要的余额/扣费证据；关联真实错误样本。固定 `[start,end)`（包含开始、不含结束）范围、UTC/指定时区、用户、Key/模型筛选、New API版本、统计基线及定价版本，确保分页完整。

**推进步骤**：

1. 取得来源快照与分页完整性证据，避免探测期间新增请求改变比较结果。
2. 独立核算输入/输出Token、原始quota、日志时间、可用汇总及适用模型价格；金额使用精确十进制。
3. 比较Portal日志、可用聚合及定价，区分字段不一致、来源不完整与当前规范明确不可用。
4. 接入可重复执行的对账适配，保存扫描通过的投影及差异报告。

**已有证据**：[P2-09说明第8～9节](18_LANG-P2-09-请求日志协议与TTFT与费用信息增强说明.md) 中，本地v0.13.2的500000 quota/USD、4050 quota实扣与0.0081 USD交叉一致；并非完全没有换算证据。当前缺的是本轮适用复验及与冻结聚合基线的衔接。

**完成标准**：预期独立、来源与Portal范围一致、数据完整性限制明确，差异可解释。旧样本不能证明其他实例或当前持续完整性，不直接把不可用的正式聚合金额改为可用。

## 8. B6：真实小样本性能冒烟

冒烟是少量请求验证链路可运行，不是容量达标证明。冷查询指缓存未命中并加载来源，热查询指相同查询身份下的缓存命中。

**缺口**：采样工具已实现，但本轮没有专用会话执行。当前客户端测量只能给出耗时和响应分类，真实缓存状态、页数、记录数与上游调用数未接入受控观测。

**需要什么**：一名测试用户有效会话、匹配运行构建、固定结束时间和真实小样本；不用等待代表性规模。当前入口使用运行时 `P210_COOKIE`，不得打印或保存其值。

**推进步骤**：在1h/24h/7d范围分别采集冷热明细，冷查询等待实际缓存TTL到期，热查询保持完整查询身份；不清理共享业务缓存。30d只检查拒绝。接入B1观测后确认缓存及上游计数；无观测时保留unknown/null。

**完成标准**：采样完成、错误及保护分类明确、固定身份/范围/构建可复现；明确真实小样本限制。若任务所需观测仍缺失，继续部分完成或BLOCKED，不能以“第二次更快”证明缓存命中。

## 9. B7：代表性真实规模性能基线

性能基线是固定数据规模和部署条件下可重复测得的延迟分布。p50/p95分别是约50%/95%请求所落入的延迟水平。

**缺口**：本地少量日志不代表未来规模；数据量、部署资源、完整观测及足量有效请求不足。当前HTTP采样无法提供所有基线必需字段，基线检查也未接通完整自动判定。

**需要什么**：明确典型及较大用户的24h/7d记录量、Key和模型分布；目标环境CPU、内存、服务拓扑、数据来源和代表性依据。可使用已有代表性测试环境，或在隔离环境通过真实业务链路积累数据；不得直接向真实数据库写伪造日志。

**推进步骤**：

1. 确认并记录数据代表性与资源条件，接入真实缓存、记录、页数和上游调用观测。
2. 1h/24h/7d各采集至少20次冷、20次热有效请求，最低120次有效样本；失败或保护拒绝另记，不计入成功延迟分布。
3. 使用最近秩算法：排序后取第ceil(n×p)项计算百分位；记录原始安全测量明细与异常比例。
4. 将已核验的代表性/资源证据接入基线检查，禁止仅设置布尔标记就把模拟或小样本升格为真实容量证据。

**完成标准**：每范围冷热均达到有效样本数，规模和资源证据明确，观测字段可靠，可发布该范围p50/p95基线。样本数量够但规模不具代表性仍BLOCKED；基线可发布也不等于性能目标通过。
