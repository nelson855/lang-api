# 前后端一体化构建与部署

## 1. 决策结论

Lang API 采用“逻辑分层、物理合包、统一编排”的方式：

- React 前端和 Spring Boot Portal API 在代码上保持独立模块；
- 前端构建产物打入 Spring Boot JAR；
- 前端页面与 `/portal/api/*` 由同一个 `lang-api` 应用提供；
- `lang-api` 最终只发布一个 JAR 和一个容器镜像；
- New API、PostgreSQL、Redis 和边缘 Nginx 保持独立容器；
- 全部服务由 Docker Compose 一次构建、一次启动和统一管理。

这里的“一次部署”是指一个版本、一个部署命令和一个 Compose 项目，不是把 New API、数据库、Redis 全部塞进同一个容器。数据库和基础服务必须继续独立，以保证数据持久化、升级和故障隔离。

## 2. 为什么这样选择

该方案符合本项目当前“尽快商用、降低维护成本、前台看起来完全自研”的目标：

1. 前端和 Portal API 原子发布，不会出现新前端配到旧接口的版本错位；
2. 浏览器只访问自身域名，不需要处理跨域资源共享（CORS）；
3. New API 地址和管理接口不会出现在浏览器网络请求中；
4. 生产环境不需要单独维护 Node.js 前端服务；
5. `lang-api` 可以按镜像版本整体回滚；
6. New API 和数据组件仍可独立升级、备份和恢复。

主要代价是：修改前端也需要重新构建并发布 `lang-api` 镜像。对于当前项目规模，这个代价低于维护两套发布链路带来的复杂度。

## 3. 逻辑架构与部署单元

### 3.1 逻辑调用关系

```text
浏览器
  ├── GET /、/dashboard、/assets/* → lang-api 静态资源
  └── /portal/api/*               → lang-api Portal API → New API 私网接口

SDK / API 客户端
  └── api.example.com/v1/*        → edge-nginx 白名单网关 → New API Relay
```

用户控制台和 Portal API 使用同一站点来源。例如：

```text
https://www.example.com/
https://www.example.com/portal/api/profile
```

前端必须使用相对路径调用接口：

```ts
fetch('/portal/api/profile')
```

禁止在前端源码或构建变量中写入 New API 私网地址，也不应把 Portal API 写成固定的完整域名。

### 3.2 物理部署关系

```text
Docker Compose 项目
├── edge-nginx     唯一公网入口、TLS、静态缓存规则、模型路径白名单
├── lang-api       Spring Boot；同时提供前端页面和 Portal API
├── new-api        私网业务底座和模型 Relay
├── postgres       持久化数据
└── redis          缓存和多节点协调
```

`lang-api` JAR 内部包含：

```text
BOOT-INF/classes/static/
├── index.html
├── assets/
└── 其他前端静态资源
```

## 4. 推荐工程结构

```text
lang-api
├── pom.xml             根构建入口
├── frontend/           React + TypeScript + Vite
│   ├── package.json
│   ├── package-lock.json
│   └── src/
├── portal-api/         Java 21 + Spring Boot
│   ├── pom.xml
│   └── src/
├── gateway/            Nginx 配置、接口白名单和错误页
├── deploy/             Compose 文件、环境模板和部署脚本
├── integration-tests/  契约测试和端到端测试
├── Dockerfile          lang-api 多阶段构建
└── docs/               项目指导文档
```

前端仍然是独立源码模块，不能把 React 源码混入 Java 目录。只有编译后的 `frontend/dist` 会进入后端制品。

## 5. 一次构建流程

根 Maven 构建作为唯一正式构建入口，顺序如下：

1. 使用锁定版本的 Node.js 和 npm；
2. 在 `frontend` 执行 `npm ci`；
3. 执行前端测试和 `npm run build`；
4. 将 `frontend/dist` 复制到 `portal-api/target/classes/static`；
5. 执行 Java 编译和测试；
6. 生成包含前端资源的 Spring Boot JAR；
7. 使用该 JAR 构建唯一的 `lang-api` 运行镜像。

建议由 `frontend-maven-plugin` 或同等 Maven 插件在 `generate-resources` 阶段构建前端，在 `process-resources` 阶段复制产物。生成文件只能进入 `target`，不得写回 `src/main/resources`，避免污染 Git 工作区。

本机正式构建命令统一为：

```bash
/Users/nelson/software/apache-maven-3.8.4/bin/mvn \
  -s /Users/nelson/software/apache-maven-3.8.4/conf/settings.xml \
  clean package
```

预期制品为：

```text
portal-api/target/lang-api.jar
```

实际文件名可以包含版本号，但 CI、Dockerfile 和部署脚本必须从同一个 Maven 项目版本推导，禁止分别手工维护。

## 6. 容器镜像规范

`Dockerfile` 使用多阶段构建：

1. 构建阶段包含 Java 21、Maven、锁定版本的 Node.js 和 npm；
2. 运行阶段只包含精简 JRE 21 和生成的 JAR；
3. 应用使用非 root 用户运行；
4. 最终镜像不得包含 `node_modules`、Maven 本地仓库、源代码、测试报告和密钥；
5. 生产前端默认不发布 Source Map；如因排障需要发布，必须限制访问并确保不含密钥；
6. Maven 私有仓库凭据通过 BuildKit secret 或 CI secret 注入，不复制进镜像层。

镜像必须使用不可变版本，例如：

```text
registry.example.com/lang-api:1.0.0
registry.example.com/lang-api:git-abc1234
```

生产环境不得只依赖会漂移的 `latest` 标签。New API、PostgreSQL、Redis 和 Nginx 镜像同样要固定版本或 digest。

## 7. 同源路由规则

### 7.1 用户站点

`www.example.com` 的推荐规则为：

| 路径 | 目标 | 说明 |
|---|---|---|
| `/portal/api/*` | Spring MVC 接口 | 用户控制面接口 |
| `/assets/*` | JAR 内静态资源 | 带内容哈希的前端文件 |
| `/actuator/health` | Spring Actuator | 仅供受控健康检查 |
| 其他页面路由 | `index.html` | React Router 单页应用回退 |

单页应用回退只能用于页面路由。不存在的 `/portal/api/*` 必须返回 JSON 404，不能错误返回 `index.html`，否则前端会把 HTML 当作接口响应解析。

### 7.2 公共模型 API

`api.example.com` 独立承载 SDK 请求，由 Nginx 按协议白名单转发到 New API。它与浏览器用户控制台不是同一个用途，因此不需要通过 Portal API，也不应启用宽泛的浏览器 CORS。

### 7.3 运行时公开配置

页面需要展示 OpenAI、Anthropic、Gemini 等 Base URL 时，由 Portal API 提供只读接口，例如：

```text
GET /portal/api/public-config
```

该接口只返回可公开的品牌、站点和 API 地址。这样同一个前端制品可部署到测试与生产环境，不必把环境域名固化在 Vite 构建变量中。

## 8. 静态资源与缓存

推荐缓存策略：

| 资源 | Cache-Control |
|---|---|
| `index.html` | `no-cache` |
| 带内容哈希的 `/assets/*` | `public, max-age=31536000, immutable` |
| 法律正文等动态接口 | 按内容版本设置短缓存或不缓存 |

发布新版本时，应先使新应用实例健康，再切换流量。回滚期间需要保证旧 HTML 所引用的静态资源仍然可用；单实例 Compose 场景可通过原子替换镜像减少不一致窗口。

## 9. 认证与安全约束

同源部署能减少跨域配置，但不能替代安全控制：

- 登录 Cookie 使用 `HttpOnly`、`Secure` 和合适的 `SameSite`；
- Cookie 的 Domain 和 Path 只覆盖所需范围；
- Portal API 必须重写或重建 New API 的 Cookie，不能把私网域名透传给浏览器；
- 状态修改接口仍需校验 Origin，并按认证方案实施 CSRF 防护；
- 不启用 `Access-Control-Allow-Origin: *`；
- 只信任来自受控 Nginx 的 `X-Forwarded-*` 请求头；
- 前端响应头中设置 CSP、`X-Content-Type-Options` 等基础安全策略；
- 不在浏览器、日志或错误页面中暴露 New API 地址、版本和响应头。

“扫描 API 看起来是自研的”应通过自有路径、字段契约、错误格式和响应头实现，不能只依赖隐藏域名。Portal API 仍必须使用接口白名单和响应字段裁剪。

## 10. 本地开发方式

开发环境无需每次修改前端都重新打 JAR：

- Vite 开发服务器监听 `localhost:5173`；
- Spring Boot 监听 `localhost:8080`；
- Vite 将 `/portal/api/*` 代理到 Spring Boot；
- 前端代码在开发和生产环境都使用相同的相对路径。

这种开发代理只用于本机效率，不改变生产环境的一体化部署结构。

## 11. 一次部署流程

推荐入口：

```bash
docker compose -f deploy/compose.yml up -d --build
```

一次部署应完成：

1. 构建指定版本的 `lang-api` 镜像；
2. 拉取已锁定版本的其他服务镜像；
3. 启动或更新 Compose 服务；
4. 等待 PostgreSQL、Redis、New API 和 `lang-api` 健康；
5. 执行首页、登录态和模型 API 的最小冒烟测试。

PostgreSQL 数据目录必须使用持久化卷或托管数据库，任何应用镜像更新都不得重建或清空业务数据。生产密钥放在环境变量、Compose secret 或外部密钥服务中，不提交到仓库。

## 12. 版本、回滚与数据库迁移

- 前端与 Portal API 共用一个应用版本号；
- 每次发布记录 `lang-api` 镜像、New API 镜像和配置版本；
- 回滚 `lang-api` 时整体回滚前端和 Portal API；
- 升级 New API 前备份数据库，并在预发布环境验证迁移；
- 自研数据库出现后，迁移脚本必须向前兼容至少一个应用版本；
- 不把“回滚容器”等同于“回滚数据库”，数据库恢复需要独立方案。

## 13. 扩容边界

第一阶段单机 Docker Compose 足够支持产品验证和初期商用，但必须保持可扩容结构：

- `lang-api` 应保持无状态，可启动多个副本；
- Session 和临时状态不能只保存在单机内存；
- 模型请求继续绕过 Portal API，避免用户控制面成为数据面瓶颈；
- 数据库、上传文件和日志不能依赖容器临时文件系统；
- 静态资源可在需要时由 Nginx 或 CDN 缓存，但制品仍由同一个应用版本生成。

当单机维护窗口不可接受或需要多节点自动恢复时，再演进为蓝绿部署、托管容器服务或 Kubernetes。当前不提前引入这些复杂度。

## 14. 验收标准

完成工程初始化后，至少满足：

- 一条 Maven 命令可同时构建前端和后端；
- 生成的 JAR 在没有 Node.js 的机器上可以启动；
- 直接访问 `/` 能返回前端页面；
- 刷新 `/dashboard` 等前端路由不会出现服务器 404；
- `/portal/api/*` 与页面同源，浏览器不需要 CORS 放行；
- 不存在的 Portal API 返回 JSON 404，而不是 `index.html`；
- 前端源码和构建产物中不包含 New API 私网地址；
- 一个 `lang-api` 镜像同时包含匹配版本的前端与 Portal API；
- 一条 Compose 命令可以启动完整环境；
- 只有边缘 Nginx 暴露公网端口；
- 数据库重启或应用升级后数据仍然存在；
- 可以使用上一个镜像版本回滚 `lang-api`。

## 15. 最终约束

后续开发必须遵守以下原则：

1. 前后端逻辑分层，但作为一个 `lang-api` 制品发布；
2. 前端只请求自身的 `/portal/api/*`，不直接请求 New API；
3. 公共模型 API 使用独立域名和路径白名单，不穿过 Portal API；
4. 一次部署通过 Compose 编排多个独立容器，不采用全组件单容器；
5. 生成物可复现、版本可追溯、应用可整体回滚、数据独立持久化。
