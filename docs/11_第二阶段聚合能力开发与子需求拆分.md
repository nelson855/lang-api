# 第二阶段聚合能力开发与子需求拆分

> 本文是 Lang API 第二阶段的开发与验收总纲。目标是在第一阶段用户闭环已经完成的基础上，利用 New API 现有底层数据建设稳定的统计、流水和模型目录聚合能力。
>
> 阶段边界见[实施顺序与 Portal API 蓝图](./03_实施顺序与Portal接口蓝图.md)，数据来源和能力分类见[QinghuaAPI 与 New API 功能对比](./02_青花API与NewAPI功能对比.md)，技术基线见[技术架构与技术选型](./04_技术架构与技术选型.md)。

## 1. 核心结论

第二阶段不重写 New API 的用户、Key、额度、日志、计费和充值能力，而是在 Portal API 中对已有数据进行组合、统计、转换和稳定封装。

第二阶段拆为 10 个子需求，按以下主线实施：

```text
LANG-P2-01 数据来源实测与统计口径冻结
  -> LANG-P2-02 聚合查询、缓存与时间范围基础设施
      -> LANG-P2-03 Dashboard 指标聚合接口
          -> LANG-P2-04 Dashboard 趋势、最近请求与前端闭环
      -> LANG-P2-05 消费汇总与钱包统一流水接口
          -> LANG-P2-06 钱包消费分析与统一流水页面
      -> LANG-P2-07 模型详情与厂商目录接口
          -> LANG-P2-08 增强模型广场前端闭环
      -> LANG-P2-09 请求日志协议、TTFT 与费用信息增强
  -> LANG-P2-10 性能、安全、端到端验收与上线收口
```

其中 `LANG-P2-01` 和 `LANG-P2-02` 是所有聚合能力的共同基础。`LANG-P2-03`～`LANG-P2-09` 可以在公共口径冻结后按三条业务线并行推进，`LANG-P2-10` 负责统一收口。

## 2. 第二阶段要交付什么

### 2.1 用户可感知的增强

第二阶段完成后，用户应当能够：

1. 按明确时间范围查看请求总数、Token 用量、消费总额、活跃 Key、成功率和平均延迟；
2. 查看请求趋势、消费趋势和最近请求，并能从概览进入请求明细；
3. 查看指定时间范围内的消费汇总；
4. 在一个统一流水中查看充值、消费和退款记录，并追溯到原始来源；
5. 查看模型详情、稳定的厂商筛选项和上游能够可靠提供的增强元数据；
6. 在请求日志中查看经实测可确认的协议类型、首 Token 延迟（TTFT）和费用信息；
7. 在 30 天等常用范围内获得稳定、可解释且不依赖浏览器全量计算的结果。

TTFT 是 Time To First Token，即从请求开始到收到第一个模型输出 Token 的耗时。只有上游存在可信字段或可以在现有链路中可靠记录时才展示，否则返回 `null`。

### 2.2 第二阶段不追求

- 不建立独立用户、API Key、额度、计费或支付系统；
- 不建设独立账务总账、授信、发票和会计科目体系；
- 不建设自有模型运营后台和完整模型主数据；
- 不建设法律文档版本、历史和用户同意审计；
- 不默认引入 OAuth、MFA、Passkey、登录设备管理和完整安全中心；
- 不默认实现 API Key 批量操作、日志长期归档、导出和在线模型 Playground；
- 不为了展示完整字段而推断或伪造 New API 没有的数据；
- 不因为未来可能需要大数据量而提前引入微服务、消息队列或数据仓库。

上述能力属于第三阶段、按需增强项或实际运营指标证明必要后再建设的内容。

## 3. 已冻结的设计决策

| 编号 | 决策 | 实现含义 |
|---|---|---|
| D01 | New API 继续作为业务数据权威 | Portal API 不双写用户、Key、额度、日志、充值和消费数据 |
| D02 | 聚合计算必须在服务端完成 | 禁止浏览器拉取全部分页日志后计算正式指标 |
| D03 | 对外使用明确时间边界 | 接口接收 `startTime`、`endTime`、`granularity`、`timezone`，快捷范围只由前端换算 |
| D04 | 时间范围采用左闭右开 | 统一按 `[startTime, endTime)` 计算，避免相邻区间重复统计 |
| D05 | 服务端内部使用 UTC | 用户时区只用于解释自然日边界和页面展示，时区使用 IANA 标识，例如 `Asia/Shanghai` |
| D06 | 金额和额度换算集中在后端 | 前端不得复制 quota、倍率、币种或精度换算公式 |
| D07 | 缺失数据显式返回 `null` | 不使用零值冒充“没有采集”或“无法确认”的字段 |
| D08 | 统一流水是只读视图 | 流水负责展示和追溯，不改变 New API 的真实入账与扣费逻辑 |
| D09 | 缓存不能改变统计口径 | 缓存键必须覆盖用户、时间范围、粒度、时区和口径版本，不缓存敏感凭证 |
| D10 | 模型增强只使用可信来源 | 第二阶段不把人工猜测的数据写成确定的模型能力 |
| D11 | 先在单体内聚合 | 优先使用现有 Portal API 和本地短期缓存，只有实测证明必要时才增加 Portal 数据库或共享缓存 |
| D12 | 对外契约继续归 Lang API 所有 | 页面和公开 DTO 不直接依赖 New API 原始响应结构 |

## 4. 第二阶段统一统计与接口约定

### 4.1 时间范围

- `startTime` 和 `endTime` 使用带时区的 ISO 8601 字符串；
- `startTime` 必须早于 `endTime`；
- `timezone` 使用 IANA 时区标识，禁止仅使用含义不完整的 `UTC+8`；
- `granularity` 使用稳定的时间粒度值，不接受 `今天`、`7D` 等页面快捷选项；
- 最大查询跨度、允许粒度及组合限制必须在 `LANG-P2-01` 中依据真实数据量冻结；
- 超出范围返回稳定的参数错误，不降级为无界查询。

### 4.2 指标口径

以下口径必须在 `LANG-P2-01` 中形成可执行定义：

| 指标 | 必须明确的内容 |
|---|---|
| 请求总数 | 哪些日志类型计入；取消、超时、上游失败是否计入 |
| Token 用量 | 输入、输出、缓存及其他 Token 的合并规则 |
| 消费总额 | 使用扣减额度还是最终结算值；退款如何反映 |
| 活跃 Key | 时间范围内产生有效请求的不同 Key 数量及去重字段 |
| 成功率 | 成功请求分子和总请求分母的状态映射 |
| 平均延迟 | 使用总耗时还是其他耗时；无效值和异常值如何处理 |
| TTFT | 字段来源、单位、覆盖协议及缺失值处理 |

任何指标不能仅根据字段名称猜测含义。无法从冻结基线可靠取得时，应明确标为暂不支持，而不是在前端模拟。

### 4.3 金额与精度

- 金额接口必须返回明确币种或额度单位；
- 服务端计算使用适合金额的十进制类型，不使用二进制浮点数累计费用；
- 汇总值与明细值采用同一换算规则和舍入策略；
- 页面格式化不能改变接口原始精度；
- 退款使用明确类型和方向，不依赖金额正负号猜测业务类型。

### 4.4 分页和排序

- 统一流水和最近请求必须有稳定排序；
- 分页边界不能因为多来源合并而重复或漏项；
- 统一流水 ID 必须稳定且能够区分来源类型；
- 对外不暴露供应商密钥、内部渠道 ID、节点名和 New API 私网信息。

### 4.5 计划接口

| 方法 | Portal API | 用途 |
|---|---|---|
| GET | `/portal/api/dashboard/stats` | 六项指标、趋势与最近请求 |
| GET | `/portal/api/account/transactions` | 充值、消费和退款统一流水 |
| GET | `/portal/api/account/consumption-summary` | 指定时间范围内消费汇总 |
| GET | `/portal/api/models/{modelId}` | 增强模型详情 |
| GET | `/portal/api/model-providers` | 稳定的模型厂商筛选项 |

请求日志现有接口继续使用 `GET /portal/api/request-logs`，通过兼容方式增加协议、TTFT 和费用等可选字段，不另建重复列表接口。

## 6. 子需求拆分

### LANG-P2-01：数据来源实测与统计口径冻结

**目标**

基于当前冻结的 New API 版本实测第二阶段所需数据，先解决“字段从哪里来、代表什么、能否稳定查询”，再开始正式聚合开发。

**实现范围**

- 实测 `/api/log/self`、`/api/log/self/stat`、`/api/data/self`、`/api/user/self`、`/api/user/topup/self` 和 `/api/pricing`；
- 保存脱敏的成功、空数据、失败和边界响应样本；
- 核对日志类型、状态、Token、费用、耗时、Key 标识、协议、TTFT 和退款相关字段；
- 定义六项 Dashboard 指标的分子、分母、单位、缺失值和异常值处理；
- 定义消费汇总与统一流水的来源映射、方向、状态和稳定 ID 规则；
- 定义时间范围、自然日、时区、粒度和最大查询跨度；
- 测量典型用户在 24 小时、7 天和 30 天范围内的上游请求数、数据量和响应时间；
- 更新 New API 兼容性记录，并标出已验证、不可用和需要降级的字段。

**边界**

- 不根据 New API 源码或旧 fixture 直接宣称真实环境行为；
- 不为缺失字段设计虚假回填；
- 不修改 New API 数据库和业务逻辑；
- 不在样本中保存用户隐私、完整 API Key、Cookie、Authorization 或供应商密钥。

**验收**

- 每个第二阶段指标都能追溯到已验证字段或明确标记为不可支持；
- 时间、金额、状态和日志类型口径没有未解释的歧义；
- 30 天范围的预计查询成本有实测证据；
- 下游 DTO 和聚合实现不再依赖未经验证的字段假设；
- 脱敏样本可用于自动化契约测试。

### LANG-P2-02：聚合查询、缓存与时间范围基础设施

**目标**

建立 Dashboard、钱包和日志增强共用的时间范围校验、分页读取、金额换算、聚合和缓存能力。

**实现范围**

- 建立统一时间范围值对象和参数校验；
- 实现 IANA 时区解析、自然日边界和夏令时测试；
- 建立统一粒度选择、分桶和空桶补齐规则；
- 建立受控的上游分页读取器，限制最大页数、最大记录数和总超时；
- 集中实现状态、日志类型、金额、Token 和耗时转换；
- 为只读聚合增加短期缓存、并发请求合并和缓存失效策略；
- 缓存键包含用户、范围、粒度、时区和口径版本；
- 记录上游调用次数、聚合耗时、缓存命中率和拒绝原因；
- 当实测证明实时聚合不满足目标时，形成增加 Portal 数据库或小时统计表的独立决策记录。

**边界**

- 不提供无界分页或全表扫描能力；
- 不缓存认证 Cookie、Access Token、完整 API Key 和原始敏感日志；
- 不让公共工具直接返回 New API DTO；
- 未经性能证据不引入消息队列、独立统计服务或数据仓库。

**验收**

- 非法时间范围、时区和粒度返回稳定自有错误；
- 相邻时间范围不会重复统计边界记录；
- 多页读取达到保护上限时明确失败，不返回伪完整数据；
- 同一用户的重复只读请求可以安全复用缓存，不会串用户；
- 夏令时、空数据、超时、部分上游失败和金额精度均有自动化测试。

### LANG-P2-03：Dashboard 指标聚合接口

**目标**

实现稳定的 `GET /portal/api/dashboard/stats`，一次返回六项指标、趋势和最近请求。

**实现范围**

- 聚合请求总数、Token 用量、消费总额、活跃 Key、成功率和平均延迟；
- 按请求粒度返回请求趋势和消费趋势；
- 返回裁剪后的最近请求；
- 对不适用或无法取得的指标返回明确可空字段和可用性信息；
- 保证汇总指标与趋势分桶使用同一统计口径；
- 支持已冻结的最大时间范围和粒度组合；
- 增加认证、越权、参数边界、上游异常和缓存测试；
- 将接口契约写入对应接口说明。

**边界**

- 不接受页面快捷范围枚举作为后端时间定义；
- 不把全部原始日志返回给 Dashboard；
- 不暴露内部渠道、节点和供应商信息；
- 不把字段缺失解释为零消费、零延迟或 100% 成功。

**验收**

- 六项指标与同一范围内的抽样日志计算结果一致；
- 趋势分桶合计与对应汇总口径一致；
- 活跃 Key 按冻结规则正确去重；
- 空数据、部分字段缺失和上游不可用具有稳定响应；
- 30 天查询不要求浏览器拉取明细，且达到冻结的性能目标。

### LANG-P2-04：Dashboard 趋势、最近请求与前端闭环

**目标**

将现有基础 Dashboard 升级为完整概览，使用户能够理解指标、切换范围并下钻到请求明细。

**实现范围**

- 展示六项指标及单位、缺失状态和口径提示；
- 提供 1H、24H、今天、昨天、7D、30D 等快捷范围；
- 前端将快捷范围转换为明确的起止时间、粒度和用户时区；
- 展示请求趋势和消费趋势；
- 展示最近请求并提供进入请求日志的入口；
- 保持余额信息与统计消费的口径说明清晰分离；
- 对加载、空数据、局部无数据、权限失效和接口错误提供明确状态；
- 保持桌面端、移动端和中英文页面可用。

**边界**

- 不在前端重新计算正式汇总指标；
- 不把缺失趋势补成看似真实的数据；
- 不为了图表效果引入与现有设计体系冲突的独立样式系统；
- 不在本需求增加高级分析、自定义报表和数据导出。

**验收**

- 每个快捷范围生成正确且可重复验证的明确时间边界；
- 指标、趋势和最近请求与接口数据一致；
- 用户时区变化后自然日范围和横轴标签正确；
- 无数据和不可用指标不会显示为误导性的零值；
- 最近请求可进入带合理筛选条件的请求日志页面。

### LANG-P2-05：消费汇总与钱包统一流水接口

**目标**

实现消费汇总和统一只读流水，使充值、消费和退款能够在同一产品契约下查询和追溯。

**实现范围**

- 实现 `GET /portal/api/account/consumption-summary`；
- 实现 `GET /portal/api/account/transactions`；
- 将充值记录、消费日志和退款记录映射为统一流水模型；
- 统一流水至少包含 `transactionId`、`occurredAt`、`type`、`amount`、`currency`、`status`、`remark` 和 `referenceId`；
- 支持已冻结的时间范围、类型筛选、稳定排序和分页；
- 为不同来源构造稳定且无冲突的交易 ID；
- 明确处理中、成功、失败、退款和未知状态映射；
- 保留能够安全返回的来源引用，支持问题排查；
- 增加跨来源排序、分页、去重、精度和权限测试。

**边界**

- 统一流水不作为会计总账或余额计算权威；
- 不修改、补记或冲正 New API 原始记录；
- 不承诺 New API 无法提供的支付渠道明细；
- 不根据金额正负号单独推断充值、消费或退款类型。

**验收**

- 消费汇总与同范围内消费明细抽样计算一致；
- 充值、消费和退款来源均能映射到统一模型；
- 跨来源分页不存在可重复复现的重复或漏项；
- 每条流水可通过安全引用追溯到来源类型和原始记录；
- 用户不能查询其他用户的消费汇总和流水。

### LANG-P2-06：钱包消费分析与统一流水页面

**目标**

升级现有钱包页面，使用户同时理解当前余额、时间范围内消费和历史资金变化。

**实现范围**

- 保留当前余额、充值状态和充值记录能力；
- 增加时间范围内消费汇总；

## 9. 第二阶段端到端验收场景

### 9.1 主链

1. 用户使用 API Key 在不同时间发起若干成功和失败的模型调用；
2. 用户打开 Dashboard，选择明确的时间范围；
3. 页面显示六项指标、请求趋势、消费趋势和最近请求；
4. 用户从最近请求进入请求日志，看到匹配的协议、Token、耗时、TTFT 和费用信息；
5. 用户进入钱包，看到同一时间范围内的消费汇总；
6. 用户在统一流水中看到充值、消费和退款记录，并能识别来源；
7. 用户进入模型广场，通过厂商筛选模型并查看模型详情；
8. 模型详情中的价格和能力与公开接入说明及实际调用结果一致；
9. 用户切换时区和时间范围，边界记录只出现在正确区间；
10. 重复查询命中安全缓存，结果与首次查询一致。

### 9.2 必须覆盖的失败链

- 非法时间范围、时区或粒度：返回明确参数错误，不触发无界上游查询；
- 查询跨度超过上限：拒绝请求并说明允许范围；
- 上游分页异常或达到保护上限：明确失败，不返回伪完整统计；
- New API 超时或不可用：返回自有错误，不泄露私网信息；
- 指标字段缺失：返回不可用或 `null`，不显示为零；
- 多来源流水存在相同原始 ID：统一 ID 不冲突，分页不重复；
- 跨用户重复查询：缓存和结果严格隔离；
- 模型 ID 含特殊字符或不存在：稳定返回自有 400/404，不形成路径穿越或任意查询；
- 历史日志没有协议或 TTFT：页面明确显示暂无数据；
- 会话过期：受保护聚合接口拒绝访问，前端回到正常认证流程。
