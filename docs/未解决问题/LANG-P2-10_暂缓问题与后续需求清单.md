## 原001：退出后旧会话仍有效

记录日期：2026-10-03。状态：**已解决**（真实验收通过，OpenSpec任务4.5已勾选）。

### 问题与影响

退出操作清除了浏览器Cookie，但没有让旧登录凭证在服务端失效。通俗地说，浏览器忘记了登录信息，服务端仍认可事先保存的那份信息。

因此，持有退出前Cookie的客户端仍可访问受保护接口。不能把“页面回到登录状态”当作“旧会话已撤销”。真实用户数据与缓存隔离检查已通过，但退出撤销要求未满足，B2及OpenSpec任务4.5仍保持未完成，不影响继续进行B3页面验证，也不代表满足上线条件。

### 已确认的现象与证据

在冻结版New API v0.13.2及当前Lang API验收构建上，两名专用普通测试身份均复现：

1. 登录并在内存中保存当次Portal Cookie。
2. 调用`POST /portal/api/auth/logout`，退出接口成功，客户端Cookie被清除。
3. 用独立客户端重放退出前的Cookie访问`GET /portal/api/profile`。
4. 两次均返回HTTP 200，而规范要求401/UNAUTHENTICATED。

独立直连New API验证也确认：上游退出返回成功后，仍接受原上游Cookie。

- [双身份断言](../../integration-tests/aggregation/report/b2/identity.json)
- [上游重放及资源检查](../../integration-tests/aggregation/report/b2/cost-and-resource-check.json)
- [B2验收报告](../../integration-tests/aggregation/report/b2/report.md)
- [正常退出规范](../../openspec/specs/portal-session-management/spec.md)
- [B2推进记录](../20_LANG-P2-10阻塞项与逐项推进方案.md)

以上证据只含安全投影，不保存真实身份或会话内容。

### 原因

Lang API此前没有服务端会话：`LANG_SESSION` Cookie直接承载New API的上游会话值，每次鉴权只调用上游`GET /api/user/self`确认身份。上游`/api/user/logout`返回成功并不真正作废会话，因此Portal侧没有任何可撤销的状态——退出只清除了浏览器Cookie。

### 采用的方案

由Lang API维护服务端会话，Redis为权威存储：

- 登录时签发随机不透明会话标识写入`LANG_SESSION`，上游会话值只保存在服务端记录中；
- 每个受保护请求先确认记录存在，再用记录中的上游会话校验用户状态；
- 退出时先删除服务端记录，再调用上游退出，上游失败也不使本地会话复活；
- 旧格式Cookie（直接承载上游会话值）在服务端无对应记录，直接拒绝，不设兼容通道；
- 存储不可用时返回稳定的`UPSTREAM_UNAVAILABLE`，不放行也不静默登出在线用户。

该方案不复制New API的用户、角色与权限体系，只管理会话生命周期。会话有效期不长于Cookie `Max-Age`，过期记录由Redis按TTL清理。

### 验证情况

后端823项测试通过（0失败、0错误、1项既有跳过），验收工具23项通过。真实Redis 7项验证通过：跨实例撤销立即可见、删除后新连接不复活、TTL自动过期；Redis重启后未删除记录仍存在、已删除记录不复活。

真实验收（复用B2两个专用测试账号与既有真实日志，未新增供应商调用）：两名身份退出后重放在profile、Dashboard、账户汇总、消费流水、请求日志、Key、Usage共7个受保护接口全部401，无一例外；两个独立容器共享同一Redis，实例1退出后实例2立即重放返回401；应用重启后重放退出前Cookie仍为401；受控失败路径下临时Key与Cookie均已清理。证据为白名单投影并通过既有敏感扫描，详见[B2报告](../../integration-tests/aggregation/report/b2/report.md)。

剩余限制：上游New API自身的退出仍不真正作废其会话，Portal侧撤销不依赖上游行为；登录限流仍为进程内状态，多实例部署时无跨实例一致性，属独立议题。

### 修复完成标准

- [x] 正常退出后，重放旧Cookie访问profile、Dashboard、账户、日志及Key接口均返回401，包括存在聚合缓存时。
- [x] 新登录正常；退出某次会话不误伤另一用户或其他独立会话。
- [x] 跨实例及重启后，已撤销会话不能恢复有效。
- [x] 重复退出、过期、伪造Cookie、存储不可用及上游退出失败的行为明确且有验证；故障时不得绕过认证。
- [x] 真实双身份验收重复执行，正常和失败路径均完成约定资源清理，证据通过敏感扫描。

复用既有测试账号和真实日志，未新增供应商调用。真实双身份验收通过后才勾选任务4.5。


## 原002：请求日志筛选生成毫秒级时间

记录日期：2026-10-03。状态：**已修复，待下一次集成浏览器回归**。

### 问题与影响

请求日志页面点击“查询”后，会将当前时间直接写进URL。前端生成的时间含毫秒，例如`2026-10-03T09:41:40.158Z`；后端只接受秒级时间。

因此，用户只要提交一次筛选，后端就返回HTTP 400，页面显示“加载失败”。这会让本应正常显示的空结果、Key筛选和模型筛选失效。

### 已确认的证据

1. 初次进入请求日志页，真实成功样本能正常显示。
2. 输入一个不存在的Key并点击“查询”后，浏览器URL包含毫秒；临时当前构建的后端日志记录`/portal/api/request-logs`返回400；页面显示“加载失败”。
3. 将同一查询的起止时间改为秒级后，真实接口正常返回，页面正确显示“当前筛选没有请求记录”。

前端`RequestLogsPage`使用`Date.toISOString()`生成时间；后端`UsageTimeRange`的`parseSecondPrecision`拒绝任何非零纳秒值。单元与可控浏览器测试此前允许毫秒格式，未覆盖该真实契约差异。

### 修复结果

已在请求日志URL解析层将合法时间统一转换为UTC秒级格式，例如`2026-10-03T09:41:40.158Z`会变为`2026-10-03T09:41:40Z`。因此筛选提交、Dashboard下钻和刷新后的URL都不会再向后端发送毫秒。

已补充并通过前端测试，覆盖带毫秒和带时区偏移的URL输入，以及Dashboard下钻请求。后端继续保持秒级限制。

### 剩余回归

- 使用下一次包含该前端构建的集成实例，复验Key、模型、结果和时间筛选都返回正常结果或空结果，不出现400。
- 复验Dashboard下钻和刷新后的URL仍可查询。

该问题不涉及真实账号、Cookie、API Key或上游原始响应。


## 原003：本地常驻容器未配置 Portal 允许来源

记录日期：2026-10-03。状态：**未解决，B3真实浏览器验收发现**。

### 问题与影响

本地常驻Lang API容器在`http://localhost:8081`提供登录页面，但没有把该来源配置到Portal允许来源中。开发环境的默认值是`http://localhost:5173`。

浏览器可以拿到CSRF令牌，但提交登录时会被来源校验拒绝，返回HTTP 403，页面只显示“请求失败，请稍后重试”。因此常驻Compose环境无法从其实际页面入口完成登录。

### 已确认的证据

- 常驻容器运行`dev`配置，未设置`PORTAL_ALLOWED_ORIGINS`。
- `application-dev.properties`的默认允许来源为`http://localhost:5173`。
- 在`http://localhost:8081`登录时，先成功请求CSRF接口，随后`POST /portal/api/auth/login`返回403。
- 为B3启动的临时实例设置`PORTAL_ALLOWED_ORIGINS=http://127.0.0.1:18081`后，同一测试账号能够正常登录。

账号密码、Cookie和请求正文未保存到本记录。

### 修复方向与完成标准

核对Compose本地启动配置，将实际公开页面来源传入`PORTAL_ALLOWED_ORIGINS`，或在开发配置中使用与项目默认入口一致的安全默认值。不得关闭来源校验来绕过问题。

修复后，常驻`localhost:8081`页面应能完成登录；来自未允许来源的跨站请求仍返回CSRF拒绝。应补充配置与真实浏览器回归，并核对生产环境继续显式配置允许来源。

## B4：固定范围真实对账

对账是从原始来源独立计算预期值，再与Portal输出比较，不能用被测服务自己的计算逻辑生成预期。

**缺口**：当前 `reconciliation` 没有完整执行适配，本轮未在当前构建上固定身份、范围、筛选和定价复验。

**需要什么**：可重复读取的真实成功日志、基础定价及必要的余额/扣费证据；关联真实错误样本。固定 `[start,end)`（包含开始、不含结束）范围、UTC/指定时区、用户、Key/模型筛选、New API版本、统计基线及定价版本，确保分页完整。

**推进步骤**：

1. 取得来源快照与分页完整性证据，避免探测期间新增请求改变比较结果。
2. 独立核算输入/输出Token、原始quota、日志时间、可用汇总及适用模型价格；金额使用精确十进制。
3. 比较Portal日志、可用聚合及定价，区分字段不一致、来源不完整与当前规范明确不可用。
4. 接入可重复执行的对账适配，保存扫描通过的投影及差异报告。

**已有证据**：[P2-09说明第8～9节](../18_LANG-P2-09-请求日志协议与TTFT与费用信息增强说明.md) 中，本地v0.13.2的500000 quota/USD、4050 quota实扣与0.0081 USD交叉一致；并非完全没有换算证据。当前缺的是本轮适用复验及与冻结聚合基线的衔接。

**完成标准**：预期独立、来源与Portal范围一致、数据完整性限制明确，差异可解释。旧样本不能证明其他实例或当前持续完整性，不直接把不可用的正式聚合金额改为可用。

## B7：代表性真实规模性能基线

性能基线是固定数据规模和部署条件下可重复测得的延迟分布。p50/p95分别是约50%/95%请求所落入的延迟水平。

**缺口**：本地少量日志不代表未来规模；数据量、部署资源、完整观测及足量有效请求不足。当前HTTP采样无法提供所有基线必需字段，基线检查也未接通完整自动判定。

**需要什么**：明确典型及较大用户的24h/7d记录量、Key和模型分布；目标环境CPU、内存、服务拓扑、数据来源和代表性依据。可使用已有代表性测试环境，或在隔离环境通过真实业务链路积累数据；不得直接向真实数据库写伪造日志。

**推进步骤**：

1. 确认并记录数据代表性与资源条件，接入真实缓存、记录、页数和上游调用观测。
2. 1h/24h/7d各采集至少20次冷、20次热有效请求，最低120次有效样本；失败或保护拒绝另记，不计入成功延迟分布。
3. 使用最近秩算法：排序后取第ceil(n×p)项计算百分位；记录原始安全测量明细与异常比例。
4. 将已核验的代表性/资源证据接入基线检查，禁止仅设置布尔标记就把模拟或小样本升格为真实容量证据。

**完成标准**：每范围冷热均达到有效样本数，规模和资源证据明确，观测字段可靠，可发布该范围p50/p95基线。样本数量够但规模不具代表性仍BLOCKED；基线可发布也不等于性能目标通过。

## B8：正式目标、负载与性能比较

**缺口**：没有明确“什么叫达标”；当前目标检查只有阻塞占位，百分位汇总的目标状态固定BLOCKED，没有目标输入与比较适配。

**需要什么**：预期用户量、并发查询数或请求频率、典型/较大用户数据规模、各范围冷热延迟目标、允许错误/拒绝比例及对应资源。具体数值由实际使用需求和测量共同确定，本文件不预设数值。

**推进步骤**：先测基线以了解现状，再确认目标与适用负载；补齐目标输入、有效性校验、逐范围比较及报告。若目标包括并发负载，增加相应负载场景，不能用单请求重复采样代替。未达标时按证据评估缓存/读取优化或另行设计预聚合。

**完成标准**：目标及资源/负载明确，基线在适用条件下产生，比较结果可复现且能给出PASS/FAIL；未确认目标或缺数据保持BLOCKED。单次5秒/总计30秒超时是查询终止预算，不是正式p95目标。

## 后续需求安排建议

B4是现有数据的准确性核验；B5.1、B5.2和基础时间边界应随准备开放的指标安排。趋势、退款、增强模型资料和增强计费可能需要新增能力，适合独立需求；充值随支付需求推进。B7/B8建议合并为性能需求，先明确典型数据量、使用负载和资源，再建立基线与目标。上述建议尚不构成范围调整或实施授权。
