# Lang API 管理员操作手册

先让用户能用起来：启动与初始化 → 确保网页登录可用 → 配置供应商渠道 → 设置模型定价和分组 → 创建普通用户并给额度 → 用普通用户走通一次调用。之后再做模型展示、注册开放、日常运维和排障。

**Lang API 当前没有独立管理员操作页面。** 管理用户、渠道和计费去 New API；Lang API 的站点、来源和公开协议等设置由运行配置控制。管理员在 Lang API 主要做普通用户使用路径的验证，不需要寻找「管理员后台」按钮。

本文基于 New API v0.13.2 中文后台，主要按钮与字段已在本地后台只读核对。示例不包含真实凭证，也不代表已经替你完成配置。

## 1. 两个平台各负责什么

| 操作 | 在哪里做 | 具体入口 |
|---|---|---|
| 上游供应商地址、密钥、可调用模型、启停、模型重定向 | New API | 控制台 → 渠道管理 |
| 输入/输出价格、按次价格、分组倍率 | New API | 系统设置 → 分组与模型定价设置 |
| 创建用户、调整账户余额、用户分组、禁用账号 | New API | 用户管理 |
| 供应商名称和模型展示资料 | New API | 模型管理；Lang API 只读取当前适配支持的资料 |
| 底层消费/错误/管理操作记录、命中渠道 | New API | 使用日志 |
| 普通用户自己的模型、密钥、调用记录、钱包 | Lang API | 模型广场、开发文档和登录后的控制台 |
| Lang API 允许来源、公开地址、发布模式、注册策略 | Lang API 运行配置 | Compose 环境配置或外部 Spring 配置，无网页设置按钮 |
| 容器健康、服务日志、备份 | 终端 | Docker Compose 命令 |

供应商是提供模型的外部服务；渠道是一份接入该服务的配置，包含地址、凭证、模型列表和分组。一个供应商可以有多个渠道。**模型管理中的「新增供应商」只登记展示资料，不能代替渠道配置。**

分组是 New API 用于路由权限和计费的分类。第一次试用让用户、渠道和实际密钥都走 `default`，最容易核对。用户登录密码、用户 API 密钥、渠道上游密钥是三种不同凭证，分别负责网页登录、用户调用、New API 调供应商。

## 2. 打开系统与管理员后台

### 2.1 已有环境

1. 启动 Docker Desktop，确认终端能执行 `docker version`。
2. 打开终端，进入仓库根目录：

```bash
cd /Users/nelson/ai-projects/2026/20260910-lang-api/lang-api
```

3. 日常同时使用 Lang API 和 New API 管理后台时执行：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  up -d --build
```

4. 检查五个服务：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml ps
```

预期 `edge-nginx、lang-api、new-api、postgres、redis` 均运行，健康检查逐步变为 healthy。构建和首次启动需要时间，先等健康后访问。

5. 浏览器分别打开：

| 地址 | 操作 |
|---|---|
| `http://localhost:8081` | Lang API 用户入口 |
| `http://127.0.0.1:13000` | New API，点 **登录**，填管理员用户名和密码，进入 **控制台** |

New API 侧边栏「管理员」下应看到 **渠道管理、模型管理、用户管理、系统设置**。看不到时确认登录的是管理员且侧边栏未收起。浏览器中管理员已有登录会话时，可直接点顶部 **控制台**。

管理员端口只绑定本机，不能把这个地址发给远程用户；普通用户也不需要进入 New API。

### 2.2 全新环境：只在尚未配置时初始化

1. 仅在 `deploy/.env` 不存在时复制模板；已有文件不要覆盖：

```bash
cp deploy/.env.example deploy/.env
```

2. 用编辑器打开 `deploy/.env`，保留默认本地域名和端口。为 `POSTGRES_PASSWORD`、`REDIS_PASSWORD` 各生成独立值，为 `SESSION_SECRET`、`CRYPTO_SECRET` 各生成独立值，填在相应等号后面。

```bash
openssl rand -hex 24
openssl rand -hex 24
openssl rand -base64 48
openssl rand -base64 48
```

前两项必须使用 URL 安全的 hex 值；每次生成的值只用于对应字段，不把它们写入手册或提交到 Git。

3. 按 2.1 节启动并打开 New API。未初始化时会进入设置流程。
4. 在管理员账号创建步骤，用户名填写自己的管理账号名（建议 3～12 位，例如 `opsadmin`），密码和确认密码填写同一至少 8 位的独立强密码；按页面步骤完成初始化。其他安装模式选项按实际运营方式选择，不把模式选择当作渠道/定价已配置。
5. 在终端执行：

```bash
curl --fail --silent --show-error http://127.0.0.1:13000/api/setup
```

初始化完成时数据中应为 `status:true`。服务 healthy 不等于管理员已初始化。

6. 保存管理员凭证到自己的密码管理工具，然后按后续章节配置。不要继续使用管理员账号作为普通用户的调用账号。

## 3. 先确保 Lang API 能登录

### 3.1 当前本地已记录的问题

默认 Compose 使用 `dev` 配置，允许的网页登录来源默认是 `http://localhost:5173`，实际集成页面却在 `http://localhost:8081`。因此页面能打开，提交登录仍可能被来源检查拒绝，表现为 HTTP 403 和 **请求失败，请稍后重试。**

来源指浏览器请求的「协议 + 主机 + 端口」，不含路径。例如 `http://localhost:8081` 和 `http://127.0.0.1:8081` 是不同来源。

**仅往 `deploy/.env` 写 `PORTAL_ALLOWED_ORIGINS` 当前不够**：Compose 主文件没有把这个变量传给 `lang-api` 容器。以下是手动本地试用的临时配置方案；它不修改业务代码，也不关闭来源检查。

### 3.2 创建本地试用覆盖文件

先检查以下文件是否已有；已有就用编辑器合并需要的字段，不要覆盖自己其他本地设置。第一次使用时，在仓库根目录执行：

```bash
mkdir -p portal-api/target/manual-use
cat > portal-api/target/manual-use/compose.yml <<'YAML'
services:
  lang-api:
    environment:
      PORTAL_ALLOWED_ORIGINS: http://localhost:8081
YAML
```

这个文件在构建产物目录中，被 Git 忽略；`mvn clean` 会删除它，清理后需要重新创建。若访问入口不是默认地址，将值换成实际网页来源；仅在确实需要两个入口时用逗号分隔精确来源。

叠加它重建 Lang API 容器：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  -f portal-api/target/manual-use/compose.yml \
  up -d --no-deps lang-api
```

这会短暂影响 Lang API 页面访问，但保留数据库和用户。等待服务健康后，在 `http://localhost:8081/login` 用第 6 节的普通账号登录，确认能进入控制台并刷新页面。

后续希望保留临时配置，完整启动也要带第三个 `-f`：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  -f portal-api/target/manual-use/compose.yml \
  up -d --build
```

若重新只用主文件启动，Compose 可能撤销这份容器环境配置。当前问题和真实浏览器回归限制见[暂缓问题与后续需求清单](../未解决问题/LANG-P2-10_暂缓问题与后续需求清单.md)。这里提供使用步骤，不代表该问题已在仓库正式修复。

## 4. 配置供应商渠道

### 4.1 先准备供应商信息

从你已经开通的供应商控制台或合同中确认：真实 API 地址、可用模型 ID、上游密钥、供应商账户余额、接口类型和计费方式。不要直接用 Lang API 的密钥填上游密钥框。

以下用「提供 OpenAI 兼容聊天接口的第三方供应商」示范；真实供应商名称、地址和模型由你替换。非兼容供应商按其 New API 渠道类型配置，不能一律选 OpenAI。

### 4.2 新建渠道

1. New API 左侧点 **渠道管理**。
2. 点击 **添加渠道**。
3. 在 **核心配置** 按表填写。

| 字段 | 怎么填 | 示例/注意 |
|---|---|---|
| 类型 | 选择供应商实际对应的类型 | 普通 OpenAI 兼容服务选择 **OpenAI**；Azure 等专用服务选专用类型 |
| 名称 | 自己能识别的渠道名 | `supplier-a-chat-test`，建议包含供应商和用途 |
| 密钥 | 供应商发给你的真实上游密钥 | 原文粘贴，别加 `Bearer `；首次只填一枚，不勾 **批量创建** |
| 组织 | 供应商要求的 OpenAI 组织标识 | 无明确要求就留空 |
| API地址 | New API 向供应商发请求的根地址 | 如供应商给 `https://你的供应商域名/v1/chat/completions`，普通 OpenAI 类型通常填根地址 `https://你的供应商域名`，由类型适配拼 `/v1/...`；特殊前缀按供应商规则填写 |
| 模型 | 这个渠道真正支持的完整模型 ID | 下拉选择；没有时使用下方 **自定义模型名称** |
| 分组 | 第一次保留 `default` | 普通用户也先用 default |
| 模型重定向 | 第一条链路先留空 | 用户请求 ID 与供应商 ID 相同时不需要映射 |
| 是否自动禁用 | 核对并按运营策略选择 | 该项只有全局自动禁用开启时才有效 |
| 默认测试模型 | 填一个已选择且供应商可调用的聊天模型 ID | 避免测试默认挑到不支持的模型 |

4. 自定义模型：在 **自定义模型名称** 输入一个完整 ID，点击 **填入**，确认它出现在上方 **模型** 中；添加多个时逐个操作。**获取模型列表** 可从支持该功能的供应商拉取模型，但不保证所有供应商都支持或所有返回模型都适合当前网关。
5. 点击底部 **提交**。成功后在列表检查渠道名称、类型、分组和状态。
6. 渠道应是 **已启用**；若是禁用状态，使用该行的启用操作恢复后再测。

官方 OpenAI 类型已内置官方地址，直连官方可留空；第三方不能留空后误调用官方。**这里的 API地址不是 `http://api.localhost:8081/v1`**，填自己的公开网关会造成错误路由或循环。

### 4.3 测试渠道

1. 在渠道行点击 **测试**；需要指定模型时使用旁边的下拉入口，选择该渠道支持的测试模型。
2. 记录是否成功和错误消息；失败就先处理地址、供应商密钥、供应商余额、模型 ID、服务器网络连通问题。
3. 测试通过后，还需按第 7 节从 Lang API 用普通用户密钥完成真实调用。管理员渠道测试不会验证普通用户权限和余额。

渠道测试可能发起实际模型请求并产生供应商费用，不要把 **测试所有渠道** 或定时测试当作免费的健康检查。

### 4.4 模型重定向：只有需要别名时才配置

例如你希望用户请求 `lang-chat-test`，供应商实际要求 `supplier-chat-id`：

1. 编辑渠道，在 **模型** 中加入对用户开放的 `lang-chat-test`。
2. **模型重定向 → 可视化 → 添加键值对**，键填 `lang-chat-test`，值填 `supplier-chat-id`；界面说明是「键为请求中的模型名称，值为要替换的模型名称」。
3. 点 **提交**。
4. 按下一节为用户调用的 ID `lang-chat-test` 配价格，并用该 ID 调用一次核对日志与扣费。

第一条链路建议先不使用别名。映射后具体定价与日志模型名可能受渠道高级设置影响，必须以实际请求验证，不凭映射规则推断扣费。

## 5. 设置模型价格和倍率

你配置的是平台向用户扣除的额度价格，不是自动同步供应商实际成本。先明确成本和你希望的用户价格，再填写；本文数字只用于说明字段。

### 5.1 给模型设置输入/输出价格

1. New API 左侧 **系统设置**。
2. 顶部选择 **分组与模型定价设置**，内部选 **模型定价设置**。
3. 使用 **可视化编辑**。
4. 在表格上方带搜索图标的输入框搜索完整模型 ID；找到后点表格中该 **模型名称**，右侧出现对应价格编辑区。
5. 没找到时点 **添加模型**，弹窗输入完整 ID，点 **确定**；然后选中这个模型。
6. **计费方式** 选 **按量计费**。
7. 在 **基础价格 → 输入价格** 填每百万输入 Token 的 USD 价格；例如 `1`。
8. 打开 **补全价格** 开关，在出现的输入框填每百万输出 Token 的 USD 价格；例如 `2`。补全就是模型输出，不是另一个模型。
9. 先不修改 **缓存读取价格、缓存创建价格、图片输入价格、音频输入价格** 等可选项；需要这些业务时另核对供应商和平台计费规则。
10. 检查 **保存预览**：本地 `500000 quota/USD` 下，输入 1、输出 2 应对应 `ModelRatio=0.5`、`CompletionRatio=2`。
11. 点击表格上方 **应用更改**，等待成功提示；重新加载页面并搜索这个模型，确认价格还在。
12. 返回 Lang API **模型广场**，默认目录缓存约 60 秒，等待后重载并检查输入/输出价格。

输入框单位是 `$/1M tokens`，不要把每千 Token 价格直接填进去。只在客户端或「模型管理」写描述，不会设置真实计费。

### 5.2 倍率和价格是什么关系

倍率是计算价格时的乘数。当前基础按量模式和本地换算下：

```text
每百万输入 Token 价格 = ModelRatio × 1000000 ÷ 500000 = ModelRatio × 2 USD
每百万输出 Token 价格 = 输入价格 × CompletionRatio
基础文本请求费用 ≈（输入 Token × 输入单价 + 输出 Token × 输出单价）÷ 1000000 × 有效分组倍率
```

例如输入 1000 Token、输出 500 Token，输入单价 1、输出单价 2，分组倍率 1，则费用约 `0.002 USD`、`1000 quota`。这是不含缓存、额外工具、阶梯表达式等项目的说明例；实际以 New API 日志和余额扣除核对。

需要「整体涨一倍」时，输入与输出单价都翻倍，或把适用分组倍率翻倍；**只改 CompletionRatio 只改变输出相对价格**。同时改模型价格和分组倍率会叠乘，必须先计算最终结果。

### 5.3 设置 default 分组倍率

1. 同一页面内部点击 **分组相关设置**。
2. **分组管理** 表格找到 `default`。
3. **倍率** 填 `1`，表示基础价；若经确认希望这组用户按基础价的 1.2 倍扣费，填 `1.2`。
4. 保持分组名称不变，第一次不要新增复杂分组或自动分组规则。
5. 点击 **保存分组相关设置**。
6. 重新加载确认数值，并用普通用户真实密钥核对一次扣费。

该倍率影响使用这个分组的相关调用，不仅是一名测试用户。下方还有 **分组特殊倍率** 和 **分组特殊可用分组**，它们可能覆盖普通倍率或改变可用分组。遇到扣费差异时也要查这两处。Lang API 模型目录展示的是基础参考价，不保证显示你的特定用户折扣。

**用户可选** 是 New API 原生令牌表单的分组选项；当前 Lang API 密钥表单没有分组选择，勾选不会自动增加 Lang API 控件。

### 5.4 按次与复杂计费

明确按请求次数收费的模型，在 **模型定价设置** 选该模型、选 **按次计费**，填写该模式显示的每次请求 USD 价格，再点 **应用更改**，重载确认并做一次扣费验证。

当前 Lang API 支持基础按量和按次价格展示；**表达式/阶梯计费、工具调用定价、增强价格** 没有完整适用展示证据。第一次试用先使用基础文本按量模型，不把复杂计费页面可配置等同于 Lang API 已能完整展示账目。

**未设置价格模型** 可帮助发现漏配项。不要依赖「自用模式」绕过定价要求向用户开放服务；未确认价格的模型先不要给用户使用。

## 6. 预建普通用户并分配测试额度

### 6.1 创建普通账号

1. New API 左侧点 **用户管理 → 添加用户**。
2. **用户名** 填 `manualuser01` 或你约定的实际登录名；建议 3～12 位，避免与 Lang API 登录长度校验不一致。
3. **显示名称** 可填 `手册测试用户`。
4. **密码** 填独立生成的至少 8 位密码；不要使用管理员密码。
5. **备注** 可填 `本地试用`，不要填写密码或密钥。
6. 点 **提交**。
7. 在用户管理搜索框输入用户名，点 **查询**，核对 **普通用户、已启用、default**。不要点 **提升** 将试用用户变成管理员。

账户由 New API 统一管理，预建后即可尝试在 Lang API 登录，不需要再在 Lang API 注册第二遍。

### 6.2 给这个用户增加测试余额

1. 找到用户行，先核对用户名和 ID，点击 **编辑**。
2. **分组** 选择 `default`；不需要重置密码时 **密码** 保持空白。
3. 在权限设置中点击 **调整额度**。
4. 弹窗 **操作** 选择 **添加**，**金额** 填预算，例如 `1`，当前 USD 展示下表示增加 1 USD 等值额度。
5. 看上方预览：原余额加上本次金额等于新余额。例如原 0.10、添加 1，结果应为 1.10。
6. 点击弹窗 **确定** 返回编辑表单，然后点击编辑表单底部 **提交**，等待成功。
7. 回用户列表确认剩余额度；再让用户刷新 Lang API 钱包确认。

**减少** 是减去指定额度；**覆盖** 是把剩余额度设置成指定值。不要把编辑页的 **金额** 直接填 `1` 当作「增加 1」；要增加时使用上面的添加流程。输入单位按当前页面的货币符号/额度展示类型确认。

展开 **使用原生额度输入** 时单位是 quota；当前本地 `500000` 对应 1 USD。不要把按 quota 的输入框当成美元。手动加额度是管理操作，不是用户实际支付的充值订单，Lang API 的充值记录或统一充值流水未必出现。

### 6.3 新用户初始额度（可选）

需要自动注册用户获得测试额度时：

1. **系统设置 → 运营设置 → 额度设置**。
2. **新用户初始额度** 输入经确认的 quota，例如本地 `50000` 约为 0.10 USD；这里虽显示 Token 标签，属于内部额度配置，不是模型实际文本 Token 数。
3. 点击 **保存额度设置**，重载确认。
4. 用新注册账号核对初始余额。不要假定此设置会追补已有账号，也不要假定管理员预建路径一定采用注册奖励逻辑；预建后仍按 6.2 核对。

当前邀请奖励、签到、兑换码和订阅不是 Lang API 已开放的用户流程，首次试用不用配置。账户有余额还不够，有限密钥也要有足够额度，并考虑模型的预扣费需求。

## 7. 用普通用户完成开通验证

按[用户使用手册](01_用户使用手册.md)操作，用普通用户账号，不用管理员账号替代：

1. 在 Lang API `/login` 登录，进入控制台，刷新页面后仍能保持登录。
2. 打开 **钱包**，确认账户余额为预期值。
3. 打开 **模型广场**，找到刚配置的完整 ID，核对基础输入/输出价格。
4. 创建 `manual-first-call` 有限密钥，分配足够完成一次请求的 quota；设置模型限制为该 ID。
5. **开发文档** 复制 Base URL，用完整密钥查 `/v1/models`，确认目标模型可见。
6. 按用户手册发送一条短非流式聊天请求，看到 HTTP 200 和真实回答；如需流式，再测试页面的流式示例。
7. Lang API **请求日志** 按 **Key 名称、模型、成功、最近 24 小时 → 查询**，核对 Token、总耗时、quota 和金额。
8. New API **使用日志** 按同一用户、令牌、模型和时间查询，核对实际渠道与费用。
9. 比较调用前后余额，确认扣减能解释；不要让这个账号同时跑其他程序，否则余额变化无法对应唯一请求。
10. **控制台 / 钱包** 检查可用字段及覆盖提示。暂不可用项保留其状态，不把它列为本次必须显示数值的成功条件。
11. 不继续使用的测试密钥，在 Lang API **停用**，需要清理时再 **删除**。

这一条真实路径能验证用户确实能用；渠道 **测试成功**、容器 healthy 或模型出现在目录，任何一项单独通过都不等于用户已开通。

## 8. 补充供应商和模型展示资料

### 8.1 登记供应商展示名称

1. New API **模型管理 → 新增供应商**。
2. **供应商名称** 填实际名称，如你确认的厂商名。
3. **描述** 填简短说明；**供应商图标** 可留空，或填界面支持的图标标识，例如 `OpenAI`。
4. **状态** 保持启用，点 **确定**。

这一步没有上游 API 密钥输入，也不会建立可调用渠道。供应商资料和渠道是独立配置。

### 8.2 登记模型展示资料

1. 同页点 **添加模型**；已有模型则搜索后编辑。
2. **模型名称** 填对用户开放的完整 ID，与渠道和定价使用的 ID 一致。
3. **名称匹配类型** 第一次选 **精确**，避免一个模糊规则影响多个模型。
4. **模型图标** 可留空；**描述、标签** 只写已确认的资料。
5. **供应商** 选择刚登记的供应商。
6. **在模型广场向用户展示的端点** 初次可留空使用默认，不借此宣称 Lang API 已开放其他协议。
7. 若是自行维护的特殊模型，按需要决定是否关闭 **参与官方同步**，避免后续同步覆盖。
8. **状态** 启用，点击 **提交**。
9. 重新加载确认；等待 Lang API 目录缓存到期后，在 **模型广场 → 厂商筛选** 核对厂商名称与关联模型。

New API 的页面明确提示：此处配置只控制模型广场展示，不影响实际调用和路由。Lang API 当前通过上游 pricing 的模型与厂商字段读取基础 ID、厂商和价格，**没有完整接入 New API 描述、标签、上下文、模态与能力等增强资料**；New API 中填了这些资料也不保证 Lang API 详情出现。当前未知信息仍会显示暂无数据。

不要为让详情「看起来完整」自行推测参数。**同步** 和官方资料更新可能影响多个模型，先确认覆盖范围再执行；不是普通用户首次能调用的必要操作。

## 9. 需要时开放用户注册

当前边测试边开发可继续预建账号，不必立刻开放注册。只有确实准备让用户自行注册时再执行本节。

### 9.1 准备法律正文

1. New API **系统设置 → 其他设置 → 通用设置**。
2. **用户协议** 输入你的真实协议正文，点 **设置用户协议**。
3. **隐私政策** 输入你的真实隐私正文，点 **设置隐私政策**。
4. 当前 Lang API 法律来源按中文 Markdown 配置，使用可由其安全渲染的正文；不要只填一个跳转网址或嵌入外部页面。
5. 重载 New API 确认保存。Lang API 法律正文默认有约 5 分钟缓存，模式切换后再验证公开页面。

这两个内容由管理员自行确认，本文不生成可直接作为正式协议的占位法律文本。

### 9.2 配置 New API 注册能力

1. **系统设置 → 系统设置 → 配置登录注册**。
2. 核对 **允许通过密码进行登录** 已允许。
3. 准备开放时启用 **允许新用户注册** 和 **允许通过密码进行注册**。
4. 这些选项没有同区统一保存按钮，修改后等待接口结果并重新加载核对状态；不要只看勾选后的临时状态。
5. 当前 Lang API 表单没有邮箱验证、Turnstile、OAuth、Passkey 或二次验证的输入流程。若上游要求这些认证能力，应继续使用兼容的预建账号路径，或先补齐 Lang API 的对应功能，不能只开启上游要求就宣称注册可用。

### 9.3 配置 Lang API 的注册和站点状态

Lang API 自身还同时要求：注册开关开启、发布模式 `PUBLIC`、用户协议和隐私政策能正常读取。默认 `PREVIEW` 下无论上游开关如何都会关闭注册。

本地测试可用第 3 节覆盖文件添加 `SPRING_APPLICATION_JSON`。用编辑器合并现有字段后，文件示例如下；将真实联系方式替换进去，已有其他 JSON 设置时合并，不能覆盖它们：

```yaml
services:
  lang-api:
    environment:
      PORTAL_ALLOWED_ORIGINS: http://localhost:8081
      SPRING_APPLICATION_JSON: >-
        {"lang.auth.registration.enabled":true,
         "lang.publication.mode":"PUBLIC",
         "lang.public.site-url":"http://localhost:8081",
         "lang.public.support-url":"mailto:替换为真实支持邮箱",
         "lang.public.supported-regions":"CN",
         "lang.public.enabled-locales":"zh-CN,en-US"}
```

`SPRING_APPLICATION_JSON` 是 Spring 接收外部配置的方式；这里直接覆盖当前开发配置中的属性。地区和语言按实际范围填写；这个示例仅用于本地验证，不是正式部署的域名、TLS 或网络方案。

1. 合并并保存后，按第 3 节带三个 `-f` 的命令重建 `lang-api`。
2. 打开 Lang API `/terms`、`/privacy`，确认出现真实正文，而不是未发布/加载失败提示。
3. 打开 `/regions`，核对地区；点击 **联系支持** 核对目标地址。
4. 打开 `/register`，确认三个字段可见，注册一个新的测试用户，跳转登录后登录并检查余额。
5. 新账号走第 7 节流程；仅看到注册按钮不算注册成功。

当前注册提交只传用户名和密码，上游额外策略变化可能仍造成失败；以新账号实际注册、登录结果为准。正式环境使用 `prod` 配置、真实 HTTPS 域名、精确允许来源与真实支持信息，参见[认证与会话闭环](../10_LANG-P1-05认证与会话闭环.md)。不应把本地 dev 容器直接作为正式发布配置。

若要回到邀请试用，设置 `lang.auth.registration.enabled=false`，按同样方式重建并确认 `/register` 提示关闭。关闭新用户注册不会自动禁用已有账号。

## 10. 日常账号、渠道和计费调整

### 10.1 用户不能登录或需要禁用

1. **用户管理** 输入用户名，点 **查询**，核对 **状态、分组、角色、余额**。
2. 需要暂停整个账号时点该行 **禁用**，按页面确认提示完成，重载确认状态；需要恢复时使用 **启用**。
3. 需要重置密码时点 **编辑**，在 **密码** 输入新的临时密码，点 **提交**，用安全方式交给用户，让用户在 Lang API **个人设置** 改成自己的密码。
4. 不修改其他凭证、分组或额度；不向普通用户授予管理员角色。

如果禁用是为了立即阻止费用，需要同时核对该用户令牌和真实网关拒绝结果；不能仅凭网页退出或改登录密码认定所有 API 密钥已失效。

New API **令牌管理** 默认管理当前登录账号的令牌，不要把管理员令牌列表当成全体用户密钥列表。某个用户泄漏的密钥，优先由用户在 Lang API **停用**；紧急情况下先暂停整个用户，再核对底层策略。不要把管理员自己的令牌当作代发给用户的密钥。

### 10.2 停用或恢复渠道

1. **渠道管理** 搜索目标渠道名称，点 **查询**。
2. 核对目标后点击 **禁用**，重载确认。
3. 若某模型只有这一条可用渠道，用户会无法调用；先确认有替代渠道或安排暂停。
4. 恢复前先修好供应商配置，点击 **启用**，再 **测试**，最后从 Lang API 普通用户路径调用。

密钥轮换：添加新的渠道配置并测试 → 用普通用户验证 → 禁用旧渠道。需要让新渠道实际接收验证请求时，还需核对路由优先级；不要仅因新建渠道测试通过就推定用户已切换到它。

### 10.3 多渠道的优先级与权重

在 **渠道管理** 同模型、同分组的渠道行可调整 **优先级** 和 **权重**：优先级决定先尝试哪批渠道，权重用于同优先级下的流量分配。第一次使用保留单渠道即可。

确需修改时记录旧值、修改目标行、等待保存结果并重载确认，再在 **使用日志** 看真实请求命中的渠道。不要把输入框已变化当成已持久化；如果错误重试、自动禁用参与了路由，命中结果还会受这些规则影响。

### 10.4 调整价格

1. 记录该模型当前输入/输出价格、default 倍率和适用特殊倍率。
2. 明确新价格和开始时间，按第 5 节修改对应模型并 **应用更改**。
3. 用隔离测试用户发送一条短请求，对比日志价格、quota 和余额变化。
4. 等目录缓存到期，核对 Lang API 展示。
5. 测试不符合预期就恢复旧价格，再复核。

只改需要的模型。**批量应用当前模型价格、上游价格同步** 会扩大影响范围，首次试用不要直接批量使用。

## 11. 日志设置与问题定位

### 11.1 开启消费日志

1. New API **系统设置 → 运营设置 → 日志设置**。
2. 核对 **启用额度消费日志记录** 为开启。
3. 有修改时点 **保存日志设置**，重载确认。
4. 发起一次受控成功调用，在 **使用日志** 和 Lang API **请求日志** 各查到记录。

历史没有记录的数据不能靠开启开关补回。**清除历史日志** 会删除记录，影响用户查日志和聚合统计，不属于日常排查步骤。

### 11.2 需要采集上游错误日志

当前 New API 默认错误日志可能关闭，Lang API 的「失败」筛选因此不一定能查到失败记录。已确认的运行开关是 `ERROR_LOG_ENABLED=true`。

需要在本地诊断时，用编辑器在第 3 节覆盖文件中增加以下服务配置，保留已有 `lang-api` 设置：

```yaml
  new-api:
    environment:
      ERROR_LOG_ENABLED: "true"
```

该片段放在顶层 `services:` 下面，与 `lang-api:` 同级。然后执行：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  -f portal-api/target/manual-use/compose.yml \
  up -d --no-deps new-api
```

这会重建 New API 容器，安排好测试时间。随后让受限测试用户做一次确定可复现的失败请求，按时间、用户、模型查 New API **使用日志 → 错误**，再查 Lang API **请求日志 → 失败**。记录为空仍需查是否在进入 New API 前被网关拒绝。

诊断结束按原策略恢复该环境值，并用同一命令重建；是否长期启用由实际日志保留和信息保护策略决定。该开关只影响之后适用路径的记录，不保证所有失败都完整覆盖，也不自动让成功率统计变为可用。

### 11.3 在 New API 查一条用户请求

1. 左侧点击 **使用日志**。
2. 顶部日期时间范围填写覆盖发生时刻的开始与结束；留意后台显示时区，本地容器使用 Asia/Shanghai。
3. **用户名称** 填用户登录名。
4. **令牌名称** 填 Lang API 中的密钥名称，如 `manual-first-call`。
5. **模型名称** 填完整 ID。
6. 需要时填 **分组、Request ID、渠道 ID**。没有可信 ID 就留空，不要把 Portal 页面错误编号机械当成同一上游 Request ID。
7. 类型选择 **消费 / 错误 / 管理** 等适用类型；首次可用 **全部**。
8. 点击 **查询**；没结果时适当放宽时间，去掉过多条件，再查一次。
9. 看 **渠道、用户、令牌、分组、类型、模型、用时/首字、输入、输出、花费、详情**。
10. 点击行最左侧展开箭头，读取该条的详细错误或计费信息。

New API 界面有首字等信息，Lang API 当前没有展示这项；它也未必等于严格的「首个输出 Token 延迟」。Portal 请求标识、网关请求标识与 New API 记录 ID 不保证都是同一个值；必要时结合时间、用户、Key、模型和渠道定位。

管理员看到的详情可能包含更多信息，分享诊断前去除密钥、用户隐私、IP 和请求正文。没有错误日志不等于没有故障。

### 11.4 终端查健康与服务日志

在仓库根目录执行；这些只读命令不会修改容器配置：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml ps
curl --fail --silent --show-error http://localhost:8081/healthz
curl --fail --silent --show-error http://127.0.0.1:13000/api/status
```

健康检查只证明探测点可响应，不能证明模型渠道、余额、网页来源配置全部正确。

分别查看最近 15 分钟日志：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  logs --since=15m --tail=200 edge-nginx

docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  logs --since=15m --tail=200 lang-api

docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml \
  logs --since=15m --tail=200 new-api
```

| 先看哪个服务 | 适合查什么 |
|---|---|
| edge-nginx | 域名路由、公开网关路径、限流、连接和超时；请求是否进入下一层 |
| lang-api | 登录、资料、密钥、目录、日志适配和聚合错误；来源/CSRF 拒绝 |
| new-api | 供应商连接、模型路由、上游错误、额度扣费和服务异常 |
| postgres / redis | 前三者日志指向数据库或会话/缓存存储故障时再查 |

CSRF 是限制浏览器跨站提交写操作的保护。登录 403 时应纠正实际 Origin 和 Cookie 配置，不关闭这项保护。

### 11.5 给自己留一条可用的问题记录

记录：页面/接口、北京时间和时区、用户 ID 或用户名、密钥名称、模型 ID、HTTP 状态、已脱敏错误摘要、可见的请求标识、当时筛选范围、复现步骤、预期与实际结果。

不要保存完整 Cookie、密码、API 密钥或供应商密钥。避免直接分享整个 `docker compose config`、完整环境变量和后台原始详情，它们可能包含凭证。复现能产生费用时使用短请求和明确预算。

## 12. 启动停止、备份和升级

### 12.1 日常启动与停止

- 没有本地覆盖时使用第 2 节启动命令；有本地覆盖时使用第 3 节带三个 `-f` 的命令。
- 只改环境配置，`up -d --no-deps 对应服务` 即可重建对应容器；改了业务代码，需要 `up -d --build` 才把新代码放进镜像。
- 宿主机 Maven 打包成功不意味着正在运行的 Docker 容器已经更新。

暂停所有服务、保留数据：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml stop
```

删除容器和网络但保留数据卷：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f deploy/compose.ops.yml down
```

日常不要添加 `-v`，它会删命名数据卷。下一次按正确的完整配置启动，数据应保留；重新看到初始化页时先停止排查，不要直接新建管理员覆盖判断。

### 12.2 用完关闭 New API 管理端口

没有本地覆盖时：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml up -d --no-deps new-api
```

已有本地覆盖、希望保留错误日志等设置时，保留覆盖但去掉 ops 文件：

```bash
docker compose --env-file deploy/.env \
  -f deploy/compose.yml -f portal-api/target/manual-use/compose.yml \
  up -d --no-deps new-api
```

然后验证：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml ps
docker compose --env-file deploy/.env -f deploy/compose.yml port new-api 3000
```

应无 `127.0.0.1:13000` 映射，管理网页不能再连接。仅关闭网页标签不等于关闭管理端口。上述 `--no-deps new-api` 只调整 New API，不撤销 Lang API 的现有来源配置；但日后完整启动仍要带对应覆盖文件。

远程服务器要用 SSH 隧道时，远端必须先存在受控的回环管理映射。若远端映射是 `127.0.0.1:13000`，在 Mac 上执行 `ssh -N -L 13000:127.0.0.1:13000 用户名@服务器地址`，再打开 Mac 的本地 13000。当前主 Compose 不映射宿主机 3000，因此不能照搬直接隧道到远端 `localhost:3000` 的写法。远端开关映射按同样受控配置处理，别把端口绑定到公网。

### 12.3 备份 PostgreSQL 和关键配置

当前用户、渠道、令牌、额度等核心数据存放在 PostgreSQL；Docker 数据卷不等于备份。

1. 在仓库根目录、数据库运行时执行以下命令。备份写到仓库外，每次创建独立目录：

```bash
umask 077
LANG_API_BACKUP_DIR="$HOME/lang-api-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$LANG_API_BACKUP_DIR"
docker compose --env-file deploy/.env -f deploy/compose.yml \
  exec -T postgres sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > "$LANG_API_BACKUP_DIR/newapi.sql"
```

2. 命令须退出成功，再检查文件非空和校验和：

```bash
test -s "$LANG_API_BACKUP_DIR/newapi.sql"
shasum -a 256 "$LANG_API_BACKUP_DIR/newapi.sql"
ls -lh "$LANG_API_BACKUP_DIR/newapi.sql"
```

非空和校验和只能证明文件存在、可跟踪，最终还需隔离恢复核验。导出失败时不要把部分 SQL 当成可用备份。

3. 单独保管密钥和运行配置：

```bash
cp deploy/.env "$LANG_API_BACKUP_DIR/deploy.env"
cp deploy/compose.yml "$LANG_API_BACKUP_DIR/compose.yml"
cp deploy/compose.ops.yml "$LANG_API_BACKUP_DIR/compose.ops.yml"
```

若使用本地试用覆盖，也复制该文件到备份目录。保存当前镜像版本、所改非敏感配置和日期。`SESSION_SECRET`、`CRYPTO_SECRET` 等关键配置不能丢失或随意重新生成；备份本身含敏感数据，放在受保护位置，不上传仓库。

4. 恢复在隔离环境中按[初始化与升级手册](../new-api/初始化与升级手册.md)的副本流程进行，并检查管理员能登录、用户/渠道/余额保留；不要直接向当前数据库覆盖导入做试验。

### 12.4 升级与开发后的验证

New API 镜像当前固定 tag 和 digest。升级顺序：备份 → 恢复副本 → 副本启动候选版本 → 兼容性和用户路径验证 → 再决定正式切换。不能只换 tag 宣称升级完成，也不能让旧镜像直接连已迁移的新数据库。

自己的 Lang API 修改后，构建和适用检查按[常用运行与验证命令](../19_常用运行与验证命令.md)选择。只编写手册不需要重新运行整套业务测试；业务修改则按变更执行对应验证，并保留本地未提交改动，提交/发布由你另行决定。

## 13. 常见故障的执行顺序

### A. 13000 后台打不开

1. `ps` 看 new-api 是否运行、healthy。
2. 用 `port new-api 3000` 查是否有管理端口映射；没有就按运行文档叠加 ops 文件打开。
3. 在本机用 `http://127.0.0.1:13000`，端口被改过则用真实值。
4. 远程访问先核对回环映射和 SSH 隧道；不要为排障把数据库或管理后台公开出去。

### B. Lang API 页面能开，登录失败

1. 用浏览器开发者工具 Network 查看 `POST /portal/api/auth/login` 的 HTTP 状态；不要复制请求正文或 Cookie。
2. 403：优先检查第 3 节，来源是否与实际浏览器地址完全一致、变量是否真的注入容器。
3. 401 或用户名密码错误：查 New API 用户状态、用户名、密码登录是否允许；避免连续失败触发限流。
4. 502/503：查 lang-api/new-api/redis 日志和健康。
5. 调整后用普通账号重新登录并刷新验证，不能只用健康接口验证。

### C. 模型广场为空或没有目标模型

1. New API **渠道管理** 确认渠道已启用，模型列表包含完整 ID，分组正确。
2. **模型定价设置** 确认价格保存；输入/补全倍率资料完整，按量/按次模式正确。
3. 等 Lang API 目录缓存约 60 秒后重新加载。
4. 仍为空看 lang-api 的 pricing 适配错误；不要通过修改前端写死模型解决。
5. New API **模型管理** 增加一个展示模型不会自动建立真实可用渠道。

### D. 管理员渠道测试成功，用户仍调用失败

1. 用户账户已启用、有足够余额。
2. 用户 Key 是完整明文，未停用/过期，有额度。
3. Key 模型/IP 限制允许这次调用。
4. 用户、实际 Key 和渠道分组兼容；首次先核对 default，不假定后台某个分组「用户可选」会改变已有 Key。
5. Base URL 是模型域名，路径是已开放的 `/v1/chat/completions`，不是网页域名或 New API 管理地址。
6. 查 New API **使用日志** 和 edge-nginx 日志，按具体错误继续定位。

### E. 扣费或价格看起来不对

1. 固定一名普通用户、一枚 Key、一条短请求和明确时间范围，排除其他并发调用。
2. 对比输入/输出 Token、原始 quota、调用前后余额。
3. 查模型输入/输出价格、有效分组倍率、特殊倍率和渠道别名。
4. 本地 `quota ÷ 500000` 可核对基础 USD；其他环境先确认实际换算及 Lang API 配置一致。
5. 区分目录基础价、日志换算金额和供应商真实账单；复杂计费不能套基础公式。
6. 钱包「正式货币金额暂不可用」是当前基线限制，不需要靠强行改倍率把它显示出来。

### F. 调用成功，统计没更新或统计失败

1. 查同一时区、时间范围、结果=成功和精确 Key 名称。
2. 日志点 **查询 / 刷新**；聚合等待约 30 秒再读取。
3. 7 天失败先缩小到 1 小时/24 小时；默认聚合保护为最多 10 页、200 条及总预算 30 秒，超过保护不会悄悄给完整统计。
4. 看 **部分覆盖 / 暂不可用** 原因，不能从空趋势推断没有消费。
5. 不直接放宽上限、修改冻结基线或填 0 掩盖缺数据；按[暂缓问题清单](../未解决问题/LANG-P2-10_暂缓问题与后续需求清单.md)区分来源限制和真实故障。
6. 请求日志筛选的秒级时间修复已在代码中，但文档记录仍待当前集成浏览器回归；运行旧镜像时查询仍可能返回 400。核对实际构建和响应，不把健康状态当作前端已更新。

### G. 想给用户充值、退款或开新协议

- 当前 Lang API 没有在线支付下单、兑换码兑换、订阅购买和退款申请流程。先用受控的管理员余额分配；单在 New API **支付设置** 填支付商信息不会自动增加 Lang API 操作页。
- 当前网关只开放模型列表和聊天完成。New API 的 Responses、Embeddings、图片、音频等能力，不会因为其后台可配置就自动通过 Lang API 网关。
- 这类需求需要单独开发和验证；手册只记录当前可操作能力。
