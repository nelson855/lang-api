## Context

第一阶段已经为 New API v0.13.2 建立基线文档、接口兼容性矩阵、脱敏样例和面向 Portal 的最小 DTO；个人日志、统计、小时用量、余额、充值记录与价格客户端也已经存在。当前不足不是“能否调用接口”，而是这些数据能否稳定支持第二阶段聚合：现有样例多为空数据或只覆盖基础成功形状，协议、TTFT、退款、状态语义、跨接口一致性和 30 天查询成本尚无完整证据。

本变更处在调查与冻结阶段。它既需要真实运行探测，又必须保持默认测试不依赖真实账户、网络或供应商；同时不能让探测过程把 Cookie、完整 Key、请求内容、个人信息或内部渠道写入仓库。需求边界见 [proposal.md](proposal.md)，行为契约见 `specs/aggregation-data-baseline/spec.md` 与 `specs/new-api-baseline/spec.md`。

## Goals / Non-Goals

**Goals:**

- 形成一套可以在冻结镜像和确定性测试数据上重复执行的六接口探测流程。
- 同时产出机器可检查的聚合基线和便于开发人员理解的中文口径、兼容性与性能文档。
- 让每个下游指标和流水字段都能追溯到具体接口、字段、样例和实测状态。
- 通过自动化校验阻止敏感数据、未解释状态和未验证字段进入正式证据。
- 给 LANG-P2-02 提供时间、金额、分页、超时和最大跨度的确定输入。

**Non-Goals:**

- 不在生产运行时加载基线文件，也不实现 Dashboard、流水、模型详情或日志增强 DTO。
- 不改变现有 New API 适配器的公开语义；只有探测发现当前映射与真实行为矛盾时，另行提出兼容修正。
- 不修改 New API 数据库来伪造生产行为；允许通过公开 API 和测试用户产生可控请求、错误、充值测试数据。
- 不把一次小数据集测量包装成容量规划结论，也不在本变更中引入预聚合表、共享缓存或队列。

## Decisions

### 1. 采用“真实探测、脱敏固化、离线回归”的三层证据链

证据链分为三个层次：

1. **真实探测**：对隔离的冻结版 New API 执行受控请求，原始响应只写入构建目录下的临时空间。
2. **脱敏固化**：将经白名单裁剪和稳定占位符替换的响应保存到 `docs/new-api/samples/aggregation/`，同时生成包含场景、版本、时间和文件摘要的 manifest。
3. **离线回归**：默认 Maven 测试读取已固化样例，验证 JSON 形状、字段类型、状态枚举、关联占位符及敏感数据禁令，不连接真实 New API。

真实探测使用测试源码中的显式 opt-in 探测入口，复用项目已有 JDK、Jackson 和测试 HTTP 基础设施，但不复用生产最小 DTO解析原始响应，否则待发现字段会在适配边界被提前丢弃。入口只有在专用开关开启且目标是明确的本地隔离地址时运行；用户名、密码和会话只从进程环境读取并停留在内存中。原始目录位于 `target/`，不得直接提交。

备选方案一是只维护 curl 操作手册，成本较低但难以保证场景、脱敏和重复次数一致；方案二是让常规 CI 访问真实环境，覆盖更自动化但需要持久凭证且易受数据和网络波动影响。两者均不作为主路径。

### 2. 使用机器可读 JSON 作为冻结基线的单一索引

新增 `docs/new-api/aggregation-baseline.json` 作为单一索引，至少包含：

- `baselineVersion`、New API release/commit/digest、实测日期和环境标识；
- 六个接口及场景的证据文件、认证、参数、分页和时间语义；
- 字段级来源、类型、单位、可空性、适用范围和四态结论；
- 六项指标的来源、纳入/排除、分子/分母、去重、单位、异常与不可用规则；
- 充值、消费、退款的方向、状态、稳定 ID 和引用规则；
- 时间、粒度、金额、舍入与性能保护边界；
- 每个性能测量记录的条件和原始结果文件摘要。

中文文档拆为 `第二阶段聚合数据兼容性矩阵.md`、`第二阶段统计与流水口径.md` 和 `第二阶段聚合性能基线.md`，用于解释结论、限制与下游使用方式，所有结论引用同一个基线版本和 JSON 条目，不在多份文档中维护相互独立的数值。

选择 JSON 而不是只写 Markdown，是为了让测试能检查必填字段、状态值、重复 ID、悬空样例引用和口径完整性。该文件是设计/验收证据，不是运行配置；后续生产配置仍按项目约束使用 `.properties`，并在 `application.properties` 及 dev/test/prod 文件中显式分离。

### 3. 场景矩阵由“接口场景”和“业务验证数据集”共同驱动

每个接口至少覆盖适用的非空成功、空数据、未认证、非法参数、边界时间/分页和上游业务失败。仅靠接口维度无法验证统计语义，因此准备以下测试用户数据集并记录其构造步骤：

- 已知数量的成功非流式请求、成功流式请求和可控上游失败；
- 两个以上 Key，包含同一 Key 多次请求，用于活跃 Key 去重；
- 跨 UTC 日界和一个夏令时切换日的时间点；
- 输入、输出及可能存在的缓存/其他 Token；
- 充值成功、失败/处理中以及退款场景；外部支付条件不足时保留条件可用结论；
- 多厂商与多计费类型的价格项；
- 空账户和典型数据量账户。

数据只能通过公开或现有运维允许的测试流程产生。若某场景无法在不修改数据库的前提下构造，记录缺失条件，不用源码或手工 JSON 把它伪装成真实证据。源码可以用于解释已观察行为，但不能代替运行结论。

### 4. 统计冻结分两步完成：候选定义与证据裁决

先从阶段文档提取每项指标的候选定义，再用实测结果逐项裁决。基线中的每项指标必须明确：权威来源、校验来源、时间字段、日志/状态集合、分子分母、去重键、单位、异常值和缺失策略。

裁决遵循以下优先级：

1. 直接且语义已验证的用户级聚合字段；
2. 可完整分页且成本在保护边界内的用户日志聚合；
3. 明确返回不可用。

不会用部分分页推算全量，也不会把字段缺失解释为零。请求总数、Token 用量和消费总额必须与同范围可获取的独立来源做抽样对账；成功率、平均延迟和活跃 Key 若必须扫描日志，则同时记录所需页数和保护上限。退款是否冲减消费必须由真实记录语义决定，而不是按数值正负猜测。

### 5. 时间与金额规则以可交接给 LANG-P2-02 为标准

时间实验明确验证上游参数单位、左右边界、默认时区、自然日和小时桶时间。对每种允许粒度形成“最小跨度、最大跨度、对齐要求、空桶策略”矩阵；Portal 对外仍使用带时区 ISO 8601 和 `[startTime,endTime)`，上游转换规则以实测为准。夏令时测试只影响自然日解释，内部计算统一 UTC。

金额实验以 `QuotaMoneyConverter` 当前的 `quota-per-usd` 为候选规则，对日志 quota、统计 quota、用户 quota、充值额度和 pricing 数值逐一确认是否同单位。最终基线明确累计阶段与展示阶段的舍入位置；任何单位或币种未确认的字段保持不可用。

### 6. 性能基线记录事实，不提前选定缓存或存储方案

对 24 小时、7 天和 30 天分别执行一次预热、一次冷启动以及默认 20 次稳定测量；每次记录接口调用数、分页数、记录数、响应字节、耗时和错误。报告给出 p50、p95 和最大值，同时记录机器、容器资源、数据规模、网络位置及 New API 配置。

测试至少包含空/小数据用户和典型数据量用户。若没有足够历史数据，30 天结果明确标记为证据不足，不能线性外推。LANG-P2-02 根据数据选择实时聚合上限、总超时和缓存 TTL；只有实测超过目标时才单独评估小时预聚合表，避免在本变更提前决定架构。

### 7. 脱敏采用白名单输出和一致占位符，不做黑名单替换

脱敏器只输出验证所需字段；用户、Key、请求、渠道和供应商标识以类型化占位符替换，例如 `<USER_1>`、`<TOKEN_1>`、`<REQUEST_1>`。同一轮探测中相同原值映射为相同占位符，以保留去重和关联关系，但映射只驻留内存，不写入磁盘。

固化前执行两类检查：一是 JSON 路径白名单与字段类型检查，二是高风险键名、Cookie/Header、长随机串、邮箱、手机号、IP、Authorization/Bearer 等模式扫描。发现命中时拒绝生成可提交证据，而不是尝试继续局部遮盖。

### 8. 验收使用“文档完整性 + fixture 契约 + 人工抽样对账”

自动化测试负责验证基线 JSON 结构、所有引用存在、样例可解析、状态值合法、每个指标定义完整及敏感模式无命中；现有 New API 客户端契约测试继续验证适配器行为。人工验收从每类数据中抽取至少一个范围，用原始临时响应按冻结公式独立计算，并与基线结论对账。

本任务不启动独立 Review 流程。正常单元/契约测试、Maven `verify`、OpenSpec 严格校验、`git diff --check` 和 `git status` 用于完成核验。

## Risks / Trade-offs

- [真实退款或支付场景缺少外部账户] → 标记为条件可用，记录缺失条件并冻结“不推断退款”的降级契约，不阻塞其他已验证口径。
- [测试数据量不足以代表 30 天生产负载] → 同时报告记录数和响应字节，禁止线性外推；LANG-P2-02 采用保守保护上限并保留后续复测入口。
- [探测工具接触敏感凭证] → 凭证只从环境进入内存，原始响应仅写 `target/`，固化输出使用白名单和双重敏感扫描。
- [New API 异步小时数据导致跨接口短时不一致] → 记录可观测延迟窗口，抽样对账使用稳定截止时间，不用实时日志补造小时桶。
- [机器可读基线与中文文档漂移] → JSON 作为唯一索引，Markdown 必须声明相同版本并引用条目；测试检查版本和证据引用。
- [一次冻结使后续调整成本增加] → 对口径分配版本，证据变化通过显式新版本处理，不在同一版本内静默改变结果。

## Migration Plan

1. 增加 opt-in 探测与脱敏入口、基线 JSON 校验模型及敏感样例检查；默认测试不访问网络。
2. 在隔离的冻结版环境准备测试用户和可复现数据集，依次采集六个接口的场景证据。
3. 固化脱敏 fixture 和 manifest，完成字段矩阵、统计/流水口径与时间金额规则。
4. 对 24 小时、7 天和 30 天执行性能测量，写入事实数据和证据限制，确定交付给 LANG-P2-02 的保护边界。
5. 运行离线契约测试、Maven `verify` 与 OpenSpec 严格校验，并对关键指标做人工抽样对账。

本变更不含部署和数据库迁移。若探测工具或文档需要回退，删除新增的测试入口和证据文件即可；既有 Portal/New API 运行行为不受影响。已经被下游引用的基线版本不得覆写，只能发布后续版本并迁移引用。
